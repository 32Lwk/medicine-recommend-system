## Root cause hypothesis（根本原因仮説）

### 1. shadow sub_route と concierge_intent の伝播乖離（Turn 4–6）

`dialogue_route_shadow` は Turn 4–6 で `sub_route=architecture`（conf 0.92–0.98, mismatch=false）を記録するが、`turns[].routing.concierge_intent` は **app_about** のまま。実行 LLM も `meta_app_about` のみ呼び出し、`meta_architecture` は未使用。

**仮説**: Turn 3 で確立した app_about セッション文脈が orchestrator / Concierge の intent 解決で優先され、intent_router_llm の architecture 判定が concierge_intent フィールドに上書き反映されていない。shadow ログと `turns[].routing` の書き込みタイミングが異なる。

### 2. 初回ターンの高レイテンシ（Turn 1–2: 21–31 s）

security（6–7 s）+ safety_gate（6–11 s）が E2E の大半。AWS ECS ステージング初回 POST で DB 読込・セキュリティチェック・セーフティゲートが直列実行された可能性。Turn 3 以降 security < 1.2 s に短縮。

### 3. conversation_history の sage_status プレースホルダ（ログ分析アーティファクト）

`conversation_history` ソースはストリーミング中の `sage_status` を assistant 返信として記録。`counseling_detail` に本文があるため `response_missing=false` だが、マージ後 `turns[]` が 11 件に膨らみ「同一入力 5 回繰り返し」と誤解されうる。evaluation.weaknesses の記述はこのアーティファクト由来と判断。

### 4. 29 分のセッション空白

Turn 2 → Turn 3 間に約 29 分。ユーザー離脱後の再開と推定。再開時も同一 session_id でメタ質問を継続しており、セッション状態は正常に維持。
