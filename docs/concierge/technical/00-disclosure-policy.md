# Concierge 技術 FAQ — 開示ポリシー

## 原則

1. **公開情報はすべて言及してよい** — Web 上・/about・公開 README 等で利用者が辿れる情報（URL、サービス名、公開されている構成説明）。
2. **深い情報は「聞かれたときだけ」** — 初回は概要（2–6 文）。「詳しく」「デプロイの流れは？」等の **深掘りトリガー** があるときだけ medium 深さ（~1500 字・複数段落）。
3. **env を読んでいるように見せない** — 回答に次を **出さない**:
   - 環境変数名（`TRANSLATION_PROVIDER` 等）
   - 「環境変数を確認しました」「サーバ設定を参照しました」
   - Secrets Manager / タスク定義 / `.env` への言及
   - 「AI が内部 API を呼んだ」系のメタ
4. **事実の言い方** — 設定の事実は **利用者向けの言葉** で述べる。
   - ❌ 設定キー名をそのまま列挙する
   - ✅ AWS ステージングでは Amazon Polly による読み上げに対応しています
   - ✅ GCP 本番・dev では Google Cloud Text-to-Speech による読み上げに対応しています
5. **非公開は答えない** — API キー、SECRET、DATABASE_URL、内部認証情報、未公開のインフラ詳細。わからない場合は「公開されている範囲では〜」と述べる。
6. **本分** — 技術 FAQ でも医薬品の症状・用法の具体助言はしない。必要なら症状入力を促す。

## 深掘りモード（implementation）

- トリガー: 「詳しく」「もっと」「デプロイ」「クロスクラウド」「CodePipeline」等、または直前が architecture カードへのフォローアップ
- 非トリガー: 「どんなツール？」「インフラ構成は？」→ 概要のみ

## 開示ポリシーの例外・特別ルール

ConciergeAgent の intent 別に、上記原則から **意図的に異なる** ルールがある。

| intent / 場面 | ルール | 根拠 |
|---------------|--------|------|
| `doc_privacy` | プライバシーポリシー md **のみ** を根拠。KB 横断 retrieve は meta 系補助のみ。条項 paraphrase 禁止 | `concierge_agent.py` — `_DOC_REFERENCE_ONLY_INTENTS` |
| `doc_terms` | 利用規約 md のみ。薬機法「合法」等の断言禁止 | 同上 + faithfulness guard |
| `doc_operator` | **氏名・所属・学年・資格はチャット上で開示しない**（ドキュメントに書いてあっても）。試験運用の個人開発 + 問い合わせ窓口を案内 | `generate_doc_answer_text` 要件 |
| `doc_operator` 導入文 | メール・フォームは **同一 status カードの sections** に記載。「直後の案内カード」表現は使わず「下記」に正規化 | `normalize_operator_intro_for_inline_card` / `build_concierge_operator_status` |
| `architecture` / `capabilities` | env 名・内部パスをサニタイズ。公開ドキュメントに無い構成は推測しない | `concierge_output_sanitize.py` |
| プライバシーポリシー第7条の連絡先 | **doc_privacy / doc_operator カード経由では正確に伝える**（チャット本文への PII 漏洩は sanitize で除去） | 公開 doc が正本 |
| 運営者情報 md の個人名 | ℹ️ モーダル・doc 直接参照では表示可。**チャット LLM 生成文には含めない** | 開示境界の二層構造 |

### 運営者個人情報の開示境界（要約）

- **チャット LLM 回答**: 個人名・大学・学年・資格 → **開示しない**。理由は「プライバシー保護のため」等で1文
- **案内するもの**: β版試験運用、個人開発、不具合報告フォーム・メール（doc 記載の表記のまま）
- **利用者が「運営者は誰？」と聞いた場合**: 上記方針 + 問い合わせ窓口。氏名で答えない

### データ × プライバシー横断質問

- 保存先・技術構成 → architecture / `04-data-security.md`
- 取得・削除権・第三者提供 → `doc_privacy`（全文参照 intent）
- 両方混在する質問 → 技術概要 + 「詳細はプライバシーポリシー（ℹ️）をご確認ください」

## Q: チャットでインフラの詳細を全部教えてもらえますか

<!-- rag-keywords: インフラ 詳細 全部 教えて 開示 深掘り -->

**回答要点**

- **初回**: 概要のみ（2–6 文）。GCP 本番 / AWS ステージング / ルールベース推奨等
- **深掘り**: 「詳しく」「デプロイ」等のトリガーがあるとき medium 深さまで
- **非公開**: API キー、DB 接続文字列、未公開インフラの細部
- **関連**: `01-cross-cloud-architecture.md`

## Q: 環境変数やサーバ設定を見て答えていますか

<!-- rag-keywords: 環境変数 設定 参照 サーバ env 見て -->

**回答要点**

- **利用者向け回答では述べない** — 「環境変数を確認しました」等のメタ禁止
- 事実は利用者向けの言葉で（例: 「AWS ステージングでは Amazon Translate を利用」）
- 出力サニタイズで env 名・Secrets Manager 言及を除去
- **関連**: `concierge_output_sanitize.py` の設計意図

## Q: 運営者の名前や大学は教えてもらえますか

<!-- rag-keywords: 運営者 名前 大学 誰 所属 開示 個人情報 -->

**回答要点**

- **チャット回答**: 氏名・所属・学年・資格は **開示しない**（doc_operator ルール）
- **理由**: プライバシー保護のため、と1文で説明
- **代替案内**: β版個人開発、不具合報告フォーム・メール（doc 記載どおり）
- ℹ️ モーダルの運営者情報 doc では公開情報として記載 — チャット LLM 生成文とは境界が異なる

## Q: プライバシーポリシーの内容を要約してもらえますか

<!-- rag-keywords: プライバシー 要約 ポリシー 条項 説明 -->

**回答要点**

- **doc_privacy intent**: md 全文を根拠に要点 5–8 項目の箇条書き（写し出しはしない）
- **禁止**: 条項の創作・paraphrase による意味変更
- 詳細は ℹ️ から全文確認を案内
- 技術 FAQ（architecture）と混在する場合は保存先（04）+ ポリシー参照（doc_privacy）に役割分担

## Q: 症状の相談と技術 FAQ を同時に聞いた場合

<!-- rag-keywords: 症状 技術 混在 境界 インフラ 頭痛 -->

**回答要点**

- 技術部分のみ回答。症状相談には踏み込まない
- 症状シグナルが混在すると末尾に「具体的な症状を入力いただければ別途ご案内」を1行追加可
- 医薬品選定は Physical 経路 — Concierge では行わない
