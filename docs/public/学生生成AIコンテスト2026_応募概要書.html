1. 解決する課題 ― 現場で見た4つの断絶

本システムは、開発者自身のドラッグストア勤務経験を出発点としています。登録販売者として店頭に立つ中で、 「薬を必要としている人に、適切な薬の情報が届いていない」場面を繰り返し目にしました。 その断絶は、次の4つに整理できます。

断絶現場で起きていること本システムの応答
理解の壁 高齢者は聴力・理解力の個人差が大きく、口頭説明を十分に受け取れないまま購入に至る。 チャットで自分のペースで読み返せる。音声読み上げ・文字サイズ調整・WCAG AA準拠コントラストを実装。
言語の壁 訪日外国人が症状を伝えられず、成分も読めないまま棚から薬を選ぶ。 日本語・英語・中国語・韓国語の4言語対応。多言語入力から日本語canonical症状へ正規化して推奨。
人手の壁 薬局の人手不足で、全ての来店客に十分な相談時間を割けない。 初期ヒアリングと情報整理をAIが担い、専門職が高度な判断に専念できる状態をつくる。
EC化の壁 ネット購入の拡大により、対面相談の機会そのものが消失している。 購入前の相談チャネルとして24時間機能し、受診が必要な場合は購入させずに医療機関へ誘導する。
この課題設定に、生成AIをそのまま当てると失敗する 汎用LLMに「頭痛の薬を教えて」と聞けば、それらしい商品名が返ってきます。しかしそれは 実在しない商品名かもしれず、年齢制限も、併用薬との相互作用も、アレルギー成分も考慮されていません。 医薬品領域におけるハルシネーションは、利用者の健康被害に直結します。 本システムの設計思想は、この一点から出発しています。

2. ソリューション概要

利用者はチャットで症状を自然文のまま入力します。システムは症状・年齢・妊娠授乳・アレルギー・服用中の薬を対話で収集し、 安全性チェックを通過した市販薬上位3件を、推奨理由・使用上の注意・受診の目安とともに提示します。

利用者入力 「頭痛が3日続いていて、38度の熱もあります」 │ ├─ ① 入力安全性検証 ────── 攻撃的入力・危機兆候を検出したら推奨を停止 ├─ ② 症状解析（LLM/NLU） ─ 表現ゆれを50種の canonical 症状へ正規化 ├─ ③ 属性確認 ──────────── 年齢・妊娠授乳・アレルギー・併用薬 ├─ ④ 禁忌・除外判定 ────── 該当薬を候補集合から完全に除外 ├─ ⑤ スコアリング（ルール） 6要素の重み付け評価でランキング └─ ⑥ 説明生成（LLM） ───── 確定済みの薬について理由を日本語化 ↓ 合計 約1〜3秒 推奨3件 ＋ 使用上の注意 ＋ 個別アドバイス ＋ 受診の目安

※ ②と⑥のみが生成AIの担当範囲です。④⑤の「どの薬を選ぶか」は一貫してルールベースが決定します。

3. 技術的独自性 ― 生成AIに「薬を選ばせない」アーキテクチャ

発表資料（宮城_柳葉魚）のノートで強調している核心は、役割分担です。 薬の選定はルールベースとスコアリングでのみ行い、会話はLLM、知識はRAGが担います。 汎用LLMに薬名を直接生成させないことで、ハルシネーションによる健康被害リスクを構造的に排除します。

3-1. 三柱の責務分離（薬選定 / 会話 / 知識）

柱担当技術独自性（やること / やらないこと）
薬選定 ルールベース＋スコアリング
（身体症状エージェント）		 薬はここでのみ決定。 禁忌除外後に6要素でランキング。同一入力には同一推奨（再現可能・説明可能）。
会話 LLM（NLU・振り分け・説明） 表現ゆれの理解と推奨理由の文章化。薬選定はしないため、存在しない薬名を生成する余地がない。
知識 RAG / Amazon Bedrock KB 医薬品FAQ・技術FAQから根拠付き回答。正確な知識で問い合わせに応答し、幻覚を抑制。

発表ノート（Slide 10）：「技術の核心は役割分担。薬の選定はルールベースとスコアリングで行い、薬はここだけで決定。会話ではLLM、知識面はBedrock KBのRAG。」

3-2. 6要素スコアリング ― 登録販売者の判断を数式化

店頭判断を重み付き評価（0.0〜1.0）として明示化。推奨理由を数値に分解できるためブラックボックスになりません。

評価要素重み内容
症状適合度+35%症状と効能効果の一致度
効能特異性+25%その症状への特化性
年齢適合性+20%年齢制限との適合
用法簡便性+5%服用回数の少なさ
副作用リスク−20%副作用レベルによる減点
相互作用リスク−10%併用薬との相互作用による減点

3-3. 会話振り分け ― SafetyGate × Triage × 専門エージェント

市販薬推奨・メンタル・緊急・案内・その他が同一入力欄から届くため、まず安全確認し、意図を5分類して専門エージェントへ渡します。 緊急時は安全性ロジックとエスカレーションにより、119・受診案内で先へ進めません（発表ノート Slide 9）。

層独自性
SafetyGate緊急性・禁忌・安全性を振り分け前に判定。危険な相談を推奨フローに入れない。
TriageAgentキーワード＋LLM判定＋キャッシュのハイブリッド。速度と精度を両立して5分類。
ChatOrchestratorコンテキスト管理・エージェント選定・ハンドオフ制御。セッション状態を維持した専門エージェント接続。
専門エージェント身体症状／メンタルケア／緊急サポート／ナビゲート／その他。責務を分離し誤誘導を抑制。

4. 安全性設計 ― 5層防御と、AIが答えない選択

医薬品を扱う以上、「推奨しない」判断の精度が、推奨の精度と同じだけ重要です。 本システムは入力から出力までの各段階に防御層を配置しています。

層機能停止・介入条件
1セキュリティ検証プロンプトインジェクション・攻撃的入力・危機兆候ワードを検出しブロック
2症状分析入力から症状を抽出できない場合は推奨せず、再入力を促す
3禁忌チェック乳児（0-3歳）は絶対禁忌／幼児（3-7歳）・妊娠中・授乳中は医師受診を即時推奨
4医薬品評価アレルギー該当成分を含む薬を候補集合から完全除外
5最終判定Red Flag症状（呼吸困難・38.5度以上・胸痛・意識障害等）検出時は推奨を停止し受診勧奨のみ返す

4-2. 人間へのエスカレーション経路

AIが答えるべきでない相談を、確実に人間へ渡す導線を実装しています。これは本システムが 「専門職を代替しない」という立場を、機能として担保するものです。

  • 薬剤師要請ボタン — 利用者が押すとそのセッションのAI自動応答が停止し、管理者・薬剤師の手動返信キューへ優先度付きで登録される。返信は「👤 薬剤師 ○○ 返信」とラベル表示され、AI発話と明確に区別される。
  • 危機検知時の自動介入 — 自傷・自殺の兆候を検出したセッションは、市販薬の案内を即時停止し、いのちの電話等の相談窓口を4言語で案内。同時に管理者ダッシュボードの優先キューへ送られ、AI応答は停止したまま人間の対応を待つ。
  • 監査ログ — 危機対応の全履歴を記録し、手順の検証と再発防止に用いる。

6-1. 生成AIの活用範囲 ― 「作品の中」と「開発の過程」

区分ツール具体的な用途
プロダクト内蔵 ChatGPT（OpenAI GPT-4o-mini API） 症状の自然言語理解（多言語入力の canonical 化）、属性抽出、推奨理由の文章生成、医薬品Q&A応答。薬の選定には一切関与させない設計。

Claude Code アーキテクチャ監査、ドキュメント整合性の検証、実装値とドキュメント記載値の突合。

生成AIを「コードを書く道具」としてだけでなく、プロジェクト固有の運用知識をスキルとして蓄積する基盤として使っている点が、 本開発における生成AI活用の特徴です。個人開発で11万行規模・15エージェント構成のシステムを保守可能な状態に保てているのは、 この体制によるものです。

7. 位置づけと今後の展望

本システムは医療行為ではなく、専門職を代替しません 提供するのは情報提供に限られ、最終判断は医師・薬剤師によるべきことを全画面で明示しています。 目的は専門性の補完と現場負担の軽減であり、医療従事者の役割を奪うことではありません。 仕様変更時には登録販売者・薬剤師・医療系研究者によるレビューを経て運用へ反映する体制を設けています。
  • 短期 — 専門家テスターからのフィードバックを反映し、推奨アルゴリズムの妥当性検証を継続。iOSネイティブアプリ（SwiftUI）の開発。
  • 中期 — 薬局・ドラッグストアでの店頭導入実証。LINE連携による相談チャネルの拡張（プロフィール記憶・相談履歴要約のエージェントは実装済み）。
  • 長期 — 自治体・地域医療のデジタル支援基盤としての活用、ECサイト連携による購入前相談の標準化。

目指す状態誰もが、どこにいても、安心して薬を選べる。 言語や年齢や時間帯を理由に、適切な情報から遠ざけられる人をなくすことが本システムの目的です。
