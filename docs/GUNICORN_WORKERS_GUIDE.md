# Gunicorn Workers設定ガイド

## 概要

このドキュメントでは、Gunicornの`GUNICORN_WORKERS`と`GUNICORN_WORKER_CLASS`について詳しく説明します。

## GUNICORN_WORKERS（ワーカープロセス数）

### とは何か？

`GUNICORN_WORKERS`は、Gunicornが起動する**ワーカープロセスの数**を指定します。

### 動作の仕組み

```
┌─────────────────┐
│  Master Process │  ← 管理プロセス（1つ）
└────────┬────────┘
         │
    ┌────┴────┐
    │         │
┌───▼───┐ ┌───▼───┐
│Worker1│ │Worker2│  ← ワーカープロセス（複数）
└───┬───┘ └───┬───┘
    │         │
    └────┬────┘
         │
    ┌────▼────┐
    │Requests │  ← リクエストを処理
    └─────────┘
```

- **Master Process**: ワーカーの管理とリクエストの振り分けを行う
- **Worker Process**: 実際にリクエストを処理するプロセス
- 各ワーカーは**独立したプロセス**として動作

### ワーカー数の影響

#### メリット
- ✅ **同時処理能力の向上**: ワーカー数が多いほど、同時に処理できるリクエスト数が増加
- ✅ **負荷分散**: リクエストが複数のワーカーに分散される

#### デメリット
- ❌ **メモリ使用量の増加**: 各ワーカーは独立したメモリ空間を持つ
- ❌ **CPU使用量の増加**: 各ワーカーがCPUリソースを使用
- ❌ **コンテキストスイッチのオーバーヘッド**: ワーカー数が多すぎると、プロセス間の切り替えコストが増加

### 推奨ワーカー数の計算

#### 基本計算式

```
推奨ワーカー数 = (CPU数 × 2) + 1
```

#### メモリ制約の考慮

```
最大ワーカー数 = (利用可能メモリ - ベースメモリ) ÷ ワーカーあたりのメモリ
```

**目安**:
- ベースメモリ: 約100MB
- ワーカーあたりのメモリ: 約50-100MB（アプリケーションの複雑さによる）

#### 現在の環境での計算

**環境情報**:
- RAM: 512MB
- CPU: 0.5
- インスタンス数: 2

**計算**:
1. CPUベース: (0.5 × 2) + 1 = **2ワーカー**
2. メモリベース: (512MB - 100MB) ÷ 100MB = **約4ワーカー**

**結論**: **2ワーカー**が適切（CPU制約とメモリの安全マージンを考慮）

### ワーカー数の調整方法

#### 環境変数で設定

```bash
GUNICORN_WORKERS=2
```

#### コマンドラインで設定

```bash
gunicorn --workers 2 app:app
```

#### 設定ファイルで設定

```python
# config/gunicorn_config.py
workers = int(os.getenv('GUNICORN_WORKERS', 2))
```

## GUNICORN_WORKER_CLASS（ワーカークラス）

### とは何か？

`GUNICORN_WORKER_CLASS`は、ワーカーがリクエストを処理する**方式**を指定します。

### 主な種類

#### 1. `sync`（同期） - 推奨

**特徴**:
- 各ワーカーが1つのリクエストを順次処理
- シンプルで安定性が高い
- CPU集約的な処理に適している

**メリット**:
- ✅ デバッグが容易
- ✅ メモリ使用量が予測しやすい
- ✅ 安定性が高い
- ✅ 追加パッケージ不要

**デメリット**:
- ❌ I/O待機中もワーカーがブロックされる
- ❌ 同時処理数 = ワーカー数

**使用例**:
```bash
GUNICORN_WORKER_CLASS=sync
```

**推奨用途**:
- CPU集約的な処理（医薬品推奨システムなど）
- 安定性を重視する本番環境

#### 2. `gevent`（非同期）

**特徴**:
- 1つのワーカーで複数のリクエストを並行処理
- イベントループベースの非同期処理
- I/O待機が多い処理に適している

**メリット**:
- ✅ メモリ効率が良い（ワーカー数が少なくて済む）
- ✅ I/O待機中に他のリクエストを処理できる
- ✅ 同時処理数 > ワーカー数

**デメリット**:
- ❌ CPU集約的な処理には不向き
- ❌ 追加パッケージ（`gevent`）が必要
- ❌ デバッグが難しい場合がある

**使用例**:
```bash
GUNICORN_WORKER_CLASS=gevent
```

**必要なパッケージ**:
```bash
pip install gevent
```

**推奨用途**:
- I/O待機が多い処理（API呼び出し、データベースクエリなど）
- チャットアプリケーション
- WebSocketアプリケーション

#### 3. `gthread`（スレッド）

**特徴**:
- スレッドベースの並行処理
- PythonのGIL（Global Interpreter Lock）の制約を受ける

**メリット**:
- ✅ I/O待機中に他のリクエストを処理できる
- ✅ メモリ効率が良い

**デメリット**:
- ❌ GILの制約でCPU集約的な処理には不向き
- ❌ スレッドセーフなコードが必要

**使用例**:
```bash
GUNICORN_WORKER_CLASS=gthread
```

### 現在の環境での推奨

**医薬品推奨システムの特徴**:
- CPU集約的な処理（医薬品データの検索、スコアリング）
- ChatGPT API呼び出し（I/O待機あり）
- データベースクエリ（I/O待機あり）

**推奨**: `sync`（同期）

**理由**:
1. CPU集約的な処理が多い
2. 安定性を重視
3. デバッグが容易
4. 追加パッケージ不要

## 現在の環境での最適設定

### 環境情報

- **プラン**: Hobby Plan - Starter
- **RAM**: 512MB per instance
- **CPU**: 0.5 per instance
- **インスタンス数**: 2

### 推奨設定

```bash
# 環境変数
GUNICORN_TIMEOUT=120
GUNICORN_GRACEFUL_TIMEOUT=30
GUNICORN_WORKERS=2          # CPU制約とメモリ制約を考慮
GUNICORN_WORKER_CLASS=sync  # CPU集約的処理に適している
```

### 設定理由

1. **ワーカー数2**:
   - CPUベース計算: (0.5 × 2) + 1 = 2
   - メモリ制約: 512MB ÷ 100MB = 約5（安全のため2に設定）
   - 2インスタンス × 2ワーカー = **合計4ワーカー**で負荷分散

2. **sync**:
   - CPU集約的な医薬品推奨処理に最適
   - 安定性が高い
   - 追加パッケージ不要

### メモリ使用量の目安

```
ベースメモリ:     約100MB
ワーカー1:        約50-100MB
ワーカー2:        約50-100MB
合計:             約200-300MB
安全マージン:     約200MB（残り）
```

### パフォーマンス監視

以下の指標を監視して、必要に応じて調整:

1. **メモリ使用率**: 80%以下を維持
2. **CPU使用率**: 平均70%以下を維持
3. **レスポンスタイム**: 平均2秒以下
4. **エラー率**: 1%以下

## トラブルシューティング

### 問題1: メモリ不足エラー

**症状**: `MemoryError` または `Out of memory`

**解決方法**:
1. ワーカー数を減らす（例: 2 → 1）
2. より大きなプランにアップグレード
3. メモリリークを確認

### 問題2: CPU使用率が高い

**症状**: CPU使用率が常に90%以上

**解決方法**:
1. ワーカー数を減らす（コンテキストスイッチのオーバーヘッドを減らす）
2. 処理の最適化（キャッシュ、非同期処理など）
3. より多くのCPUを持つプランにアップグレード

### 問題3: レスポンスタイムが遅い

**症状**: リクエスト処理に時間がかかる

**解決方法**:
1. ワーカー数を増やす（ただし、メモリとCPUの制約を考慮）
2. インスタンス数を増やす（スケーリング）
3. 処理の最適化
