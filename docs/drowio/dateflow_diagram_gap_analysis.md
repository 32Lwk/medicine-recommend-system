# データフロー図と本アプリケーションの差分分析・提案

`dateflow.drawio`（医薬品相談AIシステム - データフロー図）と実装を比較し、**不足している要素**と**図の更新提案**をまとめます。

---

## 1. 危機対応（Crisis / Emergency）

### 1.1 図の現状
- 「エスカレーション判定」「医師相談推奨」はあるが、**心理的危機**や**店舗内緊急事案**のフローは描かれていない。
- 「心臓緊急」の専用パスも図上にない。

### 1.2 実装で存在する危機対応

| 種別 | 実装場所 | 概要 | 図での不足 |
|------|----------|------|------------|
| **自殺・自傷の危機** | `crisis_detection.py`, `chat_input_validator.py` | `detect_crisis_keywords` で希死念慮・OD等を検出 → `get_crisis_support_resources` でいのちの電話等の案内。手動返信キューに `crisis_detected` で追加。 | 図に「危機キーワード検出」「危機相談案内」「危機用キュー」のプロセス・データフローが無い。 |
| **心臓緊急** | `chat_triage.py`, `llm_triage.py` | `check_heart_emergency_with_context` で心臓関連キーワードを文脈考慮して判定。緊急時は即時メッセージ＋DB更新。 | 図に「心臓緊急チェック」や「医療緊急メッセージ」の分岐が無い。 |
| **店舗内緊急事案** | `store_emergency_handler.py`, `chat_emergency_handler.py` | 不審者・傷病人・刃物・暴力・火事・窃盗等を検出し、店舗向け案内。手動返信キューに `emergency_detected` で追加。 | 図に「緊急事案検出（店舗）」や「緊急タイプ別案内」のプロセスが無い。 |

### 1.3 提案（図への追加案）
- **プロセス**: 「危機キーワード検出」（自殺・自傷）、「心臓緊急チェック」、「店舗緊急事案検出」を、入力〜エスカレーション付近に配置。
- **データフロー**: ユーザー入力 → 各検出 → 相談案内／緊急メッセージ／手動返信キュー（チャット履歴・管理者インターフェースへ）。
- **データストア**: 必要なら「危機・緊急ログ」を凡例で区別（実装では `security_logger` 等で記録）。

---

## 2. カウンセリング（Counseling）

### 2.1 図の現状
- 「質問応答処理」はあるが、**カウンセリングモード**や**話題転換**・**不眠/眠気カウンセリング**は図に無い。

### 2.2 実装で存在するカウンセリング
- **カウンセリングモード**: `chat_counseling_flow.py`, `counseling_processor.py`, `counseling_response.py`, `counseling_topic_shift.py`, `counseling_summary.py` 等。
- **流れ**: トリアージで Counseling カテゴリ → カウンセリングモード開始 → 話題転換で Physical/Emergency に切り替え可能。不眠・眠気は薬推奨へ移行。
- **危機との連携**: カウンセリング中に危機ワード検出時は `crisis_support` 応答（`get_crisis_support_resources`）。

### 2.3 提案（図への追加案）
- **プロセス**: 「カウンセリングモード」「話題転換判定」「カウンセリング応答生成」「カウンセリング完了/要約」を、質問応答・エスカレーション付近に追加。
- **データフロー**: トリアージ結果（Counseling）→ カウンセリングモード → 応答／話題転換／医薬品推奨フローまたは危機案内へ。
- **データストア**: 必要に応じて「カウンセリングログ」や「トリアージ分析」を記載（`triage_analytics`, `counseling_logger` に対応）。

---

## 3. 管理者機能（Admin）

### 3.1 図の現状
- 「管理者インターフェース」「AI制御システム」「手動返信システム」「チャットデータ」はある。
- **監視・統計・フィードバック・セッション操作**は図上で明示されていない。

### 3.2 実装で存在する管理者機能

| 機能 | 実装（例） | 図での不足 |
|------|------------|------------|
| システム状況 | `admin_system_status`（セッション数、CSV状態、手動返信キュー、AI ON/OFF） | 図に「システム状況」や「キュー状態」の参照が無い。 |
| アクセス・パフォーマンス統計 | `admin_access_stats`, `admin_performance_stats` | 「アクセス統計」「パフォーマンス統計」のデータフローが無い。 |
| ブラウザ・OS・デバイス分布 | `admin_browser_distribution`, `admin_os_distribution`, `admin_device_distribution` | 分析系の参照が無い。 |
| リアルタイム監視・エクスポート | `admin_realtime_monitoring`, `admin_export_monitoring_data` | 監視データの流れが無い。 |
| ログ・セッション・キュー一括クリア | `clear_logs` | 「クリア」操作が図に無い。 |
| AI自動応答 ON/OFF | `admin_ai_control` | 図の「AI制御」に相当するが、データフローが簡略。 |
| 医薬品相談テスト | `admin_medicine_chat` | 管理画面からの推奨テストの流れが無い。 |
| セッション一覧・削除・更新 | `get_all_sessions`, `delete_session`, `delete_all_sessions`, `update_session` | セッションCRUDと「チャット履歴/セッションデータ」との関係が不明瞭。 |
| 管理者メッセージ送信 | `admin_send_message` | 手動返信の「送信」が図では手動返信システムに含まれるが、メッセージがセッションに書き込まれる流れを明示するとよい。 |
| **フィードバック報告** | `get_feedback_reports`, `resolve_feedback`, `delete_feedback`（`feedback_routes`）＋管理画面の「不具合報告」モーダル | 図に「フィードバックDB」「不具合報告一覧・解決・削除」が無い。 |

### 3.3 提案（図への追加案）
- **プロセス**: 「監視・統計」「フィードバック報告管理」を管理者側に追加。
- **データストア**: 「フィードバックDB」（または「不具合報告データ」）を追加し、管理者インターフェースから参照・解決・削除する矢印を描く。
- **データフロー**: チャット履歴/セッションデータ → 管理者の参照／更新／手動返信送信；ユーザー → フィードバック送信 → フィードバックDB → 管理者が参照・解決。

## 4. イースターエッグ・隠し機能

### 4.1 図の現状
- 図には一切記載がない（仕様として図に含めない方針でも可）。

### 4.2 実装で存在するイースターエッグ
- **クライアント側**: `static/js/easter-eggs.js`, `checkEasterEggs(message)`。
- **主なトリガー例**: 感謝系、スネークゲーム、絵文字キャッチゲーム、花火/雪/雨、年末・誕生日・クリスマス・ハロウィン等の季節イベント、画面変形（回転・傾く・揺れる・拡大・反転・バウンス・脈動・光る）等。
- **挙動**: 発動時はサーバーに送らずクライアントで完結（一部は「感謝」で通常処理に流す）。

### 4.3 提案
- **図に含める場合**: ユーザー入力 → 「イースターエッグ判定」（クライアント）→ ゲーム/アニメーション/メッセージ表示。破線や注釈で「クライアントのみ」「サーバーを経由しない」と書くと分かりやすい。
- **図に含めない場合**: 設計書やREADMEに「イースターエッグはクライアント側の隠し機能であり、データフロー図の対象外」と一文あるとよい。

## 5. その他の不足要素

| 項目 | 実装 | 図での扱い・提案 |
|------|------|------------------|
| **診断名検出** | `chat_diagnosis_handler.py`（診断名入力時に受診推奨等） | 入力分類〜エスカレーション付近に「診断名検出」を追加。 |
| **店舗問い合わせ** | `chat_store_inquiry.py`, `store_inquiry_handler.py` | 店舗向けの「問い合わせ種別」判定と案内のプロセスを追加。 |
| **不適切メッセージ検出** | `chat_handler.py`（キーワード＋正規化）、`config/keywords.py` | 入力検証の一部として「不適切メッセージ検出」→ カウンセリング誘導またはブロックの流れを明示。 |
| **入力検証・ブロック** | `chat_input_validator.py`（`validate_and_block_input`、危機検出・ブロックリスト） | 「入力検証」を入力分類の前段として明示。 |
| **安全性チェックの詳細** | `enhanced_safety_checker.py`（禁忌・医師受診必須・重篤副作用・相互作用）、`absolute_blocklist` | 図の「安全性チェック」から「禁忌DB／ブロックリスト」への参照を描く。 |
| **フィードバック送信** | `feedback_routes.py`（`submit_feedback`）、ユーザー画面の「不具合報告」 | ユーザー → フィードバック送信 → フィードバックDB のフローを追加。 |
| **ログ記録の内訳** | `recommendation_logger`, `security_logger`, `structured_logger`, `triage_analytics` | 「ログ記録」を「推奨ログ」「セキュリティログ」「トリアージ/カウンセリング分析」等に分けて記載してもよい。 |

## 6. 図の更新優先度の提案

1. **必須に近い（仕様理解のため）**
   - 危機対応: 自殺・自傷の危機検出と相談案内、心臓緊急、店舗緊急事案の分岐。
   - カウンセリング: カウンセリングモード・話題転換・危機連携。
   - 管理者: フィードバック報告の取得・解決・削除とフィードバックDB。
   - 入力まわり: 入力検証・危機検出の位置づけ。

2. **あるとよい**
   - 管理者の監視・統計・リアルタイム監視・エクスポート。
   - 診断名検出、店舗問い合わせ、不適切メッセージ検出。
   - 安全性チェックと禁忌/ブロックリストの関係。

3. **任意**
   - イースターエッグ（クライアントのみの注釈）。
   - ログの種別（推奨・セキュリティ・分析）の細分化。

---

## 7. ファイル名・フォルダ名の補足

- `docs/drowio/dateflow.drawio` → フォルダ名は `drawio`、ファイル名は `dataflow.drawio` にすると意味が伝わりやすいです（前回指摘のとおり）。

以上を反映すると、データフロー図が実装と一致し、危機対応・カウンセリング・管理者機能・イースターエッグなどを第三者に説明しやすくなります。
