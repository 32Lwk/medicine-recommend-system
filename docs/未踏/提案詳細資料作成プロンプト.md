# 未踏 提案プロジェクト詳細資料 作成プロンプト

以下の指示に従い、**まず提案者（私）に関する情報をすべて質問してから**、回答をもとに提案詳細資料の文案を作成してください。  
**技術的な側面・開発スケジュール・コスト試算など未確定の部分は、対話しながらAIが案を提示し、提案者が考えや制約を伝えて改善していく形で決めていきます。**

---

## 前提

- **技術的根拠**: `docs/LaTex/Engineering Documents.tex`（ハイブリッド医薬品推奨システムの技術文書）の内容を参照する。
- **構成・要件**: `docs/未踏/竹内PM.md` に記載の「提案プロジェクト詳細資料の書き方」および「提出前チェックリスト」に完全に沿う。
- **出力**: A4・10.5pt以上・8ページ程度（10ページ以内）、冒頭に開発テーマ名と提案者名を記載した提案プロジェクト詳細資料の文案。

### メモの記録と参照（必須）

- **記録先**: `docs/未踏/docs/` に、現状の草案・計画・提案・「どうすべきか」のメモを**常に記録**する。対話のたびに更新し、フェーズをまたいでも内容が引き継がれるようにする。
- **記録する内容の例**: 提案者情報の要約、技術・スケジュール・コストの案と合意内容、文案の要約や差分、次のアクション・未決事項・PMへの要望メモなど。
- **ファイルの例**: 内容に応じて使い分ける（例: `phase1_answers.md`＝提案者回答、`phase2_plan.md`＝技術・スケジュール・コストの合意・案の履歴、`proposal_draft.md`＝文案または文案の更新履歴、`memo.md`＝総合メモ・どうすべきか・次のステップ）。
- **参照のタイミング**: **次のフェーズに進む前に**、`docs/未踏/docs/` 内の既存メモを読み、そこに書かれた合意・草案・未決事項を踏まえてから進める。セッションが変わっても、このフォルダを読めば文脈が復元できるようにする。

## フェーズ1: 提案者情報の収集（必須）

**開始時**: `docs/未踏/docs/` に既存メモがあれば読み、続きや未決事項があれば踏まえる。  
**提案詳細資料の文案を作成する前に、以下の質問にすべて答えてもらうこと。**  
回答が得られない項目は「未回答」「該当なし」などと明記し、後で本人が追記できるようにする。  
**終了時**: 提案者の回答（または要約）を `docs/未踏/docs/phase1_answers.md` などに記録する。

### 1. 基本情報
- 氏名（提案者名）
- 生年月日（2026年4月1日時点で満25歳未満であることの確認用）
- 連絡先（メールアドレス等、必要に応じて）
- 所属（大学名・学部・学科・学年、または勤務先、フリーターの場合は「無職」等）

### 2. 学歴・経歴
- 最終学歴および在学中の学校・学部・学科・学年
- これまでの進路（中高・大学入試、転学部・休学・留年などの有無）
- 研究室在籍の有無（在籍中または在籍予定の場合、研究室名・指導教員名・研究テーマの概要）
- 職歴（アルバイト・インターン・正社員など、本プロジェクトに関連しそうなもの）

### 3. 技術スキル・開発経験（⑤腕前の証明に直結）
- 使用できるプログラミング言語と習熟度（初心者・中級・上級など）
- 使用したことのあるフレームワーク・ライブラリ・ツール（Web、DB、API、ML等）
- これまでに作成したプログラム・ソフトウェア・ハードウェアの概要（名称、役割、公開URLやリポジトリがあれば）
- 本プロジェクトで使用予定の技術（Python, Flask, PostgreSQL, OpenAI API等）の経験の有無と程度
- 登録販売者資格の有無および取得時期（本プロジェクトの背景と直結するため）
- その他、システム開発に関して「できること」を証明できる経験（授業・演習・卒研・個人開発・コンテスト等）

### 4. 採択歴・受賞歴・資格
- 未踏・未踏ジュニア・未踏アドバンスト等の採択歴
- プログラミング・コンテスト・ハッカソン・論文賞等の受賞歴
- 資格（情報処理、登録販売者、その他）
- セキュリティ・キャンプ・U-22・AKATSUKI等の参加・修了歴

### 5. 本プロジェクトとの接点
- 本テーマ（医薬品推奨・セルフメディケーション・OTC）を選んだ理由・経緯
- ドラッグストア・薬局・医療系アルバイト・研究の経験の有無と内容
- 「説明時間の不足や人手不足によるケアの限界」を実感した経験の有無

### 6. プロジェクト遂行上の特記事項（⑥に記載する内容）
- 学生の場合: 学業との両立の考え方、指導教員がいる場合はその了解の有無
- 組織に属している場合: 仕事との両立、上司の了解の有無
- 開発期間中の進学・就職・転職・転居の予定の有無
- 未成年の場合: 保護者の了解の有無
- 複数人で開発する場合: メンバー構成・役割・知り合った経緯・各メンバーの動機と貢献
- PM・IPAへの要望や、申請者固有の事情（ある場合）

### 7. 開発環境・時間（④の進め方に直結・対話で詰める前提）
- 主に開発を行う場所（自宅・大学・コワーキング等）
- 使用予定の計算機環境（OS、ハードの概要）※決まっていなければ「未定・相談したい」で可
- 開発にかけられる時間（週あたりの時間帯とおおよその時間数、学期・試験期による変動があれば）
- 開発期間の希望（何ヶ月程度か、開始希望時期）※概算で可。後でフェーズ2で一緒に詰める

### 8. IT以外の勉強・特技・生活・趣味（⑦用）
- ソフトウェア以外の勉強（専攻以外の分野、独学など）
- 特技・スポーツ・文化系の活動
- 普段の生活で大切にしていること、アルバイト・ボランティア等
- 趣味（ITと直結しないものも含む）
- 上記が本プロジェクトの成果やモチベーションにどう影響しそうか（思いつく範囲で）

### 9. 将来のITについて思うこと・期すること（⑧用）
- IT・ソフトウェア・社会について、提案内容に縛られず思っていること
- 未踏修了後にやりたいこと（就職・起業・研究・未踏アドバンスト等）
- 将来のIT人材・エコシステムについての考え（任意）

### 10. その他、提案者について伝えたいこと
- 長すぎる自分史は不要とされているが、PMが「この人に任せたい」と思えるような、略歴・人柄・強みで押さえておきたい点
- 上記のどれにも当てはまらないが、提案書に書いておきたいこと

## フェーズ2: 技術・スケジュール・コストの対話的検討（未確定部分の提案と改善）

**開始時**: `docs/未踏/docs/` のメモ（特に `phase1_answers.md` と `phase2_plan.md`）を読み、既に出ている案・合意・未決事項を把握してから進める。**あわせて `docs/未踏/docs/koubo.md`（公募要領）を参照する。** 開発期間・契約条件・申請金額の算定（時間単価等）・プロジェクトの規模・範囲は公募要領に従う。  
**技術的な側面・開発スケジュール・コスト試算は「まだ決まっていない」前提で進める。**  
AIは `Engineering Documents.tex` とフェーズ1の回答（および上記メモ）、**koubo.md の該当箇所**を踏まえ、**案を提示 → 提案者が制約・希望・疑問を伝える → 案を修正・改善** を繰り返し、合意できる形にしていく。  
**対話のたびに**: 提示した案・提案者の反応・合意した内容・「どうすべきか」のメモを `docs/未踏/docs/phase2_plan.md` に追記・更新する。フェーズ3に進む時点で、確定した技術・スケジュール・コストをメモに明示しておく。

### 2.1 AIが対話で提案・改善する項目

| 項目 | AIの役割 | 提案者が伝えるとよいこと |
|------|----------|---------------------------|
| **技術的な側面** | 技術スタック・開発手法・マイルストーン・スコープ（どこまでを未踏期間で実装するか）の案を提示。Engineering文書の「現状実装」と「将来計画」を整理し、9ヶ月で現実的な範囲を提案。 | 使いたい/使いたくない技術、学業・本業との兼ね合い、経験の有無による希望 |
| **開発スケジュール** | 開発線表（いつまでに何をするか、月単位）の案を提示。試験期・就活・進学などの変動を聞いて組み込む。 | 忙しい月・集中できる月、マイルストーンの前倒し/後ろ倒しの希望 |
| **コスト試算** | 作業時間の見積もり（週○時間×○ヶ月）と申請金額の概算、必要経費の内訳表の案を提示。**`koubo.md`（公募要領）の時間単価・費用の支払い・プロジェクトの規模・範囲を参照する。** | 月あたりの作業時間の上限、かかりそうな経費（機器・API・書籍等）の有無 |

### 2.2 対話の進め方（AIへの指示）

1. **初回**: 技術アプローチ・スケジュール・コストの「第一案」を提示する。根拠（Engineering文書の該当箇所・提案者の週時間・未踏の期間）を簡潔に示す。
2. **提案者の反応を受けて**: 「ここは変えたい」「この時期は無理」「もっと短い期間で申請したい」などに応じて、スケジュール・スコープ・時間数・経費を修正した第二案を出す。
3. **詰まったら**: 選択肢を2〜3パターンに分けて提示し（例: スコープ多め／少なめ、期間9ヶ月／6ヶ月）、メリット・デメリットを短く述べて選んでもらう。
4. **合意した内容**: フェーズ3で文案にそのまま反映する。後から「やっぱり変えたい」があれば、その部分だけ対話で修正し、文案を更新する。

### 2.3 参照する技術内容（Engineering Documents.tex より・案の土台）

- **テーマ**: ハイブリッド医薬品推奨システム（ルールベーススコアリングと動的フォールバックによる数理的安全性保証とセルフメディケーション支援）
- **背景**: 少子高齢化・人手不足、OTC誤選択・市販薬依存の増加、登録販売者としての実感
- **目的・目標**: LLMをNLUに限定し、推奨はルールベーススコアリングで数学的保証；5層防御、ハイブリッドNLU、禁忌・アレルギー即時除外
- **技術アプローチ**: 5段階パイプライン、信頼度関数に基づくLLMフォールバック、ルールベーススコアリング（将来は潜在空間ベクトル類似度の統合計画）
- **技術スタック（文書上の例）**: Python 3.11, Flask, PostgreSQL/SQLite, OpenAI API, Render.com 等 → 対話で「このまま使う／一部差し替える」を決める
- **世の中への出し方**: 提案者の意向を聞きつつ、フリー/OSS/ビジネス/学会等の案を提示
- **開発線表・予算**: 文書に具体的な月別線表や金額がなくても、フェーズ2の対話で「作業時間・必要経費」を一緒に試算する
- **斬新さ・効果**: 数理的安全性保証、医療機関負担軽減、多言語対応、薬局業務効率化など（文書の「期待される効果」を要約）

## フェーズ3: 提案詳細資料の文案作成

**開始時**: `docs/未踏/docs/` のメモ（`phase1_answers.md`・`phase2_plan.md` および既存の文案メモ）を読み、提案者情報と合意済みの技術・スケジュール・コストを把握してから文案を作成する。**あわせて `docs/未踏/docs/koubo.md`（公募要領）を参照する。** 応募要件・提出資料の形式・提案プロジェクト詳細資料の作成方法・入力項目等は公募要領に合わせる。  
フェーズ1の回答と**フェーズ2で合意した技術・スケジュール・コスト**（いずれもメモに記録されている内容）を反映し、竹内PM.md の構成に沿って提案詳細資料の文案を作成する。  
**終了時**: 文案または文案の要約・更新履歴を `docs/未踏/docs/proposal_draft.md`（または既存の `proposal.md`）に記録する。追修正した場合も、その都度メモを更新する。

### 竹内PM.md に沿った構成

| 項目 | 内容 |
|------|------|
| ⓪ タイトル | どんなテクノロジーでどんな課題を解決するか一目で分かる簡潔なタイトル |
| ① 何を作るか | 背景（なぜ）・目的（何を）・目標（どこまで）を専門家でない人に分かるように。ビジュアル活用を推奨。長すぎる自分史は避ける。 |
| ② どんな出し方を考えているか | フリーソフト/OSS/ビジネス/起業/学会等の想定と、修了後のアクション |
| ③ 斬新さの主張・期待される効果 | ①・②を受けた内容。既存調査を踏まえた上で、技術力・技術背景が透けて見えるように。 |
| ④ 具体的な進め方と予算 | (1)開発場所 (2)計算機環境 (3)言語・ツール (4)分担（複数人の場合） (5)開発手法（あれば） (6)開発線表 (7)開発時間帯・時間数 (8)予算内訳の表 ※いずれもフェーズ2で合意した内容を記載 |
| ⑤ 提案者の腕前を証明できるもの | 作成したプログラム・ソフトの説明、スキル、採択歴・受賞歴など（フェーズ1の回答を反映） |
| ⑥ プロジェクト遂行にあたっての特記事項 | 学業/職場/保護者との両立、了解、進学・就職等の予定（フェーズ1の回答を反映） |
| ⑦ IT以外の勉強・特技・生活・趣味 | 簡潔に、人柄が伝わるように（フェーズ1の回答を反映） |
| ⑧ 将来のITについて思うこと・期すること | 提案内容に縛られず自由に。文章力も見る。 |

### 注意事項（竹内PM.md より）

- 願望だけでは提案書にしない。「何をどこまで作るか」を明確に書く。
- ⑤では、デモが環境依存で手間がかかる場合はデモ動画を推奨。
- 生成AIで書いた部分があれば明記する。
- 提出前チェックリストの各項目を満たしているか最終確認する。

## 使い方

1. **フェーズ1**: このプロンプトをAIに渡し、「フェーズ1の質問をすべて一度に提示してください」と依頼する。提示された質問に、自分用のメモや下書きとして回答する。
2. **フェーズ2**: 回答を渡し、「フェーズ2に従い、技術・スケジュール・コストの第一案を提示してください」と依頼する。制約・希望・「ここを変えたい」を伝え、対話しながら案を修正・改善する。納得できる案ができたら「この内容で確定」と伝える。
3. **フェーズ3**: 「フェーズ3に従い、フェーズ1の回答とフェーズ2で決めた内容で、提案詳細資料の文案を作成してください」と依頼する。
4. **追修正**: 文案の文言調整・ページ割り・図表の挿入・技術・スケジュール・コストの微修正が必要なら、「④の開発線表を〇月からに変更」「予算内訳に〇を追加」などと指示して修正する。技術・スケジュール・コストを大きく変える場合は、再度フェーズ2のように対話で詰めてから文案を更新する。修正のたびに `docs/未踏/docs/` の該当メモを更新する。
