## 未踏が重視している点（公募要領・PMメッセージより）

- **人材**: 25歳未満の「伸びる才能」の発掘・育成が第一義。成果も重要だが、計画の緻密さ・腕前の証明・世の中への出し方が採択の判断材料。
- **提案内容**: 独創性・革新性、社会的インパクト、イノベーション創出の可能性。**「何をどこまで作るか」が明確**であること。願望だけでは不可。
- **書類**: ①背景・目的・目標を専門家でない人に分かるように、**ビジュアル活用**。③斬新さは**既存調査**の上で主張。④計画の緻密さ（開発線表・時間数・予算）。⑤**腕前の証明**（デモ動画推奨）。②世の中への出し方・修了後のアクション必須。
- **審査**: 各PMが独自基準で審査。書面審査→二次審査（ヒアリング・プレゼン）。記載漏れ・様式不備で事前にはねられることがある。

## 1. 追加すべき内容

| 項目 | 追加内容 | 理由 |
|------|----------|------|
| **① 何を作るか** | **図・ビジュアル**（システム構成図、5層防御のイメージ、入力→推奨までの流れ） | 竹内PM: 「ビジュアルを活用すればすぐ分かるのに、活用していない提案はイメージがつかみにくい」。専門家でない人に伝えるために有効。 |
| **①** | **社会課題の数字を冒頭に**（例: 市販薬依存が2014年0%→2022年65.2%、登録販売者求人倍率3.56倍） | 背景の説得力と社会的インパクトが一気に伝わる。Engineering文書に既にある数値を使える。 |
| **③ 斬新さ・効果** | **既存調査の明示**（純LLM型・純ルールベース型・既存OTC相談ツールの比較を1段落で整理） | 「既存調査がきちんと行っていないと、斬新さや効果の主張は一気に崩れます」（竹内PM）。phase2_planの「①・③用: 既存調査」をそのまま使う。 |
| **③** | **数値目標の明示**（禁忌判定99%以上維持、アレルギー100%、応答時間の目安など） | 計画の具体性が増し、「どこまで測るか」が審査で評価されやすい。phase2_planの評価指標を要約して記載。 |
| **② 世の中への出し方** | **修了後のアクションを1文で具体化**（例: 学会名・OSSライセンス方針・未踏アドバンストの言及） | 「作ってみるだけでは困る」。現案で十分だが、「どの学会を想定しているか」「OSSはどの部分をいつ」など一言あるとより良い。 |
| **④ 進め方・予算** | **開発線表を表形式で明示**（月単位・何をするか） | 計画の緻密さは採択の判定材料。phase2_planの月別マイルストーンをそのまま表で載せる。 |
| **④** | **AWSの具体的な利用形態を1行**（例: EC2/ECS で Web アプリホスティング、または Lambda + API Gateway 等） | 「AWSでデプロイ」だけだと抽象的。何をどこで使うかが書いてあると見通しが良い。 |
| **⑤ 腕前** | **デモ動画を用意する旨を明記**（2～3分、環境依存を避けるため） | 竹内PM: 「デモが環境依存で手間がかかる場合はデモ動画を推奨」。本番URLに加え、動画があると安心。 |
| **⑤** | **受賞歴・本番公開を「証明」として強調**（学生生成AI最優秀賞、椙山ビジコン優秀賞、doda審査員特別賞、本システム公開URL） | 採択歴がなくても、コンテスト賞・実運用中のシステムで腕前を証明できる。 |
| **⑧ 将来のIT** | 現状のphase1回答で十分内容がある。**文章力・独自の視点**がそのまま伝わるように整える。 | 「自由論文課題のようなもの」「文章力も見る」。手を入れすぎず、本人の言葉を活かす。 |

## 2. 改善すべき点

| 項目 | 改善内容 | 理由 |
|------|----------|------|
| **① 何を作るか** | **「何をどこまで作るか」を1文で冒頭または要約に書く** | 「なにをどこまで作るかが結局分からない」「願望だけを書いてくる」と注意されている。例: 「既存のルールベース推奨に潜在空間ベクトル類似度を統合したハイブリッドを実装し、安全性指標を維持したまま推薦精度を評価可能な形で完成させる。」 |
| **全体** | **生成AI利用の有無を明記** | 竹内PM: 「背景説明などに生成AIを使った場合などはそう明記しておいたほうが安全」。使っていないなら「本文は本人執筆」など一言あるとよい。 |
| **③ 斬新さ** | **技術力・技術背景が透けて見えるように** | 「斬新さの主張の裏に提案者の技術力・技術背景が透けて見えます」。数式（5層防御・ハイブリッドスコア）や設計判断（LLMをNLUに限定する理由）を短文で示す。 |
| **④** | **第①項の開発物の内容を④に書かない** | 「ここに第①項で書くべきこと（具体的な開発物の内容）を書く人がいます。審査のときに困ります」。④は場所・環境・言語・分担・手法・線表・時間・予算に限定。 |
| **⑥ 特記事項** | **学業両立・試験期（7月末・1月末）の記載を確実に** | 「学生の場合は学業との両立や関係、指導者がいれば指導者の了解について簡単に記載」。試験で開発が少なくなる月を明記済みなら、その旨を⑥にも書く。 |
| **セキュリティ・キャンプ** | **記載しない方針で問題ないが、⑤または⑥に1行あると「発掘経路」としてプラスになる可能性** | 公募要領上必須ではない。書けば未踏と相性の良い経路として評価されうる。記載するかは提案者判断で可。 |

## 3. 加えると良い技術スタック・開発まわり

| 分野 | 追加候補 | 効果 |
|------|----------|------|
| **テスト・品質** | **pytest / 単体・統合テスト** を④(3)または(5)に明記 | 計画の緻密さ・品質意識が伝わる。「Phase1→2→3で段階的マージ、各段階で評価可能」と合わせて書くと良い。 |
| **CI** | **GitHub Actions**（テスト自動実行・リント）を1行でも | 一人開発でも、CIがあると開発の見通しの良さが伝わる。 |
| **ベクトル周り** | **pgvector**（PostgreSQL拡張）または **埋め込み用カラム・インデックス** の言及 | 潜在空間を「既存DB拡張」で実現する方針が技術的に具体的になる。 |
| **AWS** | **利用サービスを1つに絞って記載**（例: 「AWS ECS または EC2 で Web アプリをホスティング」） | 「AWSでデプロイ」を具体化し、予算・線表との整合が取りやすい。 |
| **API・再現性** | **API仕様の明文化・ドキュメント化**を開発線表の12月タスクに含める | OSS化・他者利用を意識した計画として伝わる。 |

※ 技術を増やしすぎると「9ヶ月でやり切れるか」を疑われうるため、**既存スタック＋テスト/CI/ベクトル保存の明示**程度に抑えるのが無難。

## 4. 加えると「面白い」「差別化」になる内容

| **社会課題の数字** | 市販薬依存65.2%、求人倍率3.56倍、医薬品過剰摂取による緊急搬送増等を①の冒頭で使用 | 社会的インパクトが数字で伝わる。 |
| **判断の哲学** | 「判断を自動化したいのではなく、人が誤らないための構造を作りたい」を①または③に1文で | phase1に既にある。PMメッセージの「人が誤らないための構造」と一致し、印象に残る。 |
| **修了後の広がり** | 未踏アドバンスト・OSS・学会に加え、「薬局向けAPI」「自治体・健康増進事業との連携」等を1行 | 将来のインパクトのイメージが湧く。 |

## 6. まとめ：優先してやること

1. **①に図を1枚以上入れる**（システム構成 or 5層防御 or フロー）
2. **①の冒頭に「何をどこまで作るか」を1文で書く**
3. **③に既存調査（純LLM/純ルール/既存OTC）の比較を入れる**
4. **④に開発線表を表で明示し、AWSの利用形態を1行書く**
5. **⑤にデモ動画・本番URL・受賞歴を明記する**
6. **生成AI利用の有無を明記する**
7. 余力があれば: 社会課題の数字、国際的通用性、評価のオープン化、補助薬の将来拡張を各1文ずつ追加

これらはすべて、**現行の phase2_plan・phase1_answers・Engineering 文書の内容で足りており、文案に「どう書くか」を反映するだけ**で対応可能です。新規で大きな機能を約束する必要はありません。

## 8. 確認・質問事項（提案者への確認希望）

以下の点について、ご意向や追加情報があれば教えてください。

1. **背景の地域格差の数値**: 薬局・ドラッグストアの立地偏在や過疎地の相談機会不足について、厚労省等の具体的な統計（例：人口当たり薬局数の地域差、無薬局地区の数など）をご存知でしたら追記できます。

2. **「本提案がもたらす価値」の冒頭表現**: 本文では「本サービスが目指す最大の価値は」としていますが、提案段階では「本提案が目指す」の方が適切かもしれません。どちらを採用しますか。

3. **目標のPhase時期**: Phase1（7〜8月）、Phase2（9月）、Phase3（10〜11月）としました。開発線表（④）との整合は取っていますが、Phase3を10月のみ／11月のみに狭めるなど、調整の要望があればお知らせください。

4. **生成AI利用の明記**: 竹内PM.mdでは「背景説明などに生成AIを使った場合は明記する」とあります。本提案書で生成AIを利用している部分があれば、⑥特記事項や末尾に1文追加することを推奨します。

5. **他に追記・修正したい点**: 上記以外に、①「何を作るか」で強調したい表現や、削除したい重複表現などがあればお知らせください。
