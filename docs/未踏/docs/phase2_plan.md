## 第一案: 技術的な側面

### スコープ（未踏の9ヶ月で「どこまで作るか」）

Engineering文書の**現状**（すでに実装済み）と**将来計画**を整理し、9ヶ月で現実的に届く範囲を以下にした。

- **すでにあるもの（土台）**  
  - 5段階パイプライン（リスク→NLU→禁忌→スコアリング→top3）  
  - ハイブリッドNLU（辞書＋信頼度関数、閾値未満でLLMフォールバック）  
  - **ルールベース**スコアリング（症状適合度・効能特異性・年齢・用法・副作用・相互作用）  
  - 5層防御（入力検証・NLU・禁忌・アレルギー・最終判定）  
  - 多言語（4言語）、本番はPostgreSQL、Renderデプロイ  

- **未踏期間で実現する「核となる成果」（提案のメイン）**  
  - **位置づけ（提案者方針）**: 既存のルールベーススコアリングを土台とし、未踏期間では**潜在空間への移行（部分的統合）**により、症状に対して最も適した医薬品が推奨されるシステムを目指す。  
  - 潜在空間の利点として、(1)既存システムの短所を補完できる、(2)LLM（NLU）と相性が良く、症状文から最適な医薬品を推奨できる、(3)計算量を削減し推奨処理の高速化が期待できる、を提案書で明示する。  
  1. **潜在空間ベクトル類似度の実装**（Phase 1）  
     - 医薬品効能の埋め込み事前計算（text-embedding-3-small）、Vector DB 的利用または既存DB拡張  
     - 推論時のユーザークエリ埋め込みとコサイン類似度計算  
     - 既存ルールベースと**並行評価**できる形で実装  
  2. **ハイブリッドスコアリングの統合**（Phase 2）  
     - \( S(m,u) = \alpha \cdot \text{sim}(v_u, v_m) + \beta \cdot \text{coverage}(S_u, E_m) - \delta \cdot \text{penalty}(m,u) \) の実装  
     - 信頼度に応じた動的重み \(\alpha(\sigma), \beta(\sigma)\) の導入  
  3. **評価とチューニング**（Phase 3）  
     - 既存テスト・シナリオを使ったA/B的比較、重みパラメータの探索  
     - 安全性指標（禁忌・アレルギー検出率）の維持確認  

- **あくまで副次・時間があれば**  
  - 音声入力、Alembic によるスキーマ管理、Redis キャッシュなどは「将来改善」として記載し、未踏期間では着手しないか最小限に留める。

|------|------|------|
| 言語 | Python 3.11 | 現状維持 |

| DB | PostgreSQL（本番）, SQLite（開発） | 現状維持。埋め込みベクトル保存用カラムまたは別テーブルを追加 |
| API | OpenAI API（GPT-4o-mini, text-embedding-3-small）, DeepL API | 埋め込み利用を正式に組み込み |

- **開発手法**: 既存リポジトリをベースにした継続開発。テスト（単体・統合・シナリオ）を拡充しつつ、Phase1→2→3 の順でマージしていく。

### 技術面で「PM受け」が良さそうな書き方の提案

1. **「何をどこまで作るか」を1文で言えるようにする**  
   例: 「既存のルールベース推奨システムに、潜在空間ベクトル類似度を統合したハイブリッドスコアリングを実装し、安全性指標を維持したまま推薦精度を評価可能な形で完成させる。」
2. **数理的な保証を前面に**  
   - 5層防御の式（\( \prod L_i \)）と「推奨はルール＋類似度で決まり、LLMはNLUに限定」を図か短文で明示する。  
   - 「判断を自動化したいのではなく、人が誤らないための構造を作りたい」という一言を①または③に活かす。
3. **既存調査をきちんと書く**  
   - 純LLM推奨・純ルールベース・既存OTC相談ツールや論文を簡潔に比較し、「だからハイブリッド＋NLU限定」という流れにすると、斬新さと効果の主張が崩れにくい（竹内PMメッセージ③）。
4. **制約・限界を正直に書く**  
   - 「潜在空間は現時点で未実装であり、未踏期間で実装・統合する」と明記すると、計画の見通しの良さが伝わる。

## 追加で提案したいこと・改善したい点

1. **タイトル案（⓪用）**  
   - 例: 「ルールベースと潜在空間ベクトルを統合したハイブリッドOTC医薬品推奨システムの実装と評価」  
   - または: 「数理的安全性を保証するハイブリッド医薬品推奨システムの実装（潜在空間スコアリングの統合）」  
   - 「どんなテクノロジーでどんな課題を解決するか」が一目で分かる簡潔なものにすると、PMメッセージの要望に沿う。

2. **④(2) 計算機環境**  
   - phase1では「自宅のPCおよびノートパソコン」のみ記載。OS（Windows/macOS/Linux）とメモリ・CPUの概略（例: 8GB以上、など）を1行でも書いておくと、審査で安心。

3. **④(5) 開発に使う手法**  
   - 「既存リポジトリの継続開発」「単体・統合・シナリオテストの拡充」「Phase1→2→3の段階的マージ」などを1～2文で書くと、計画の緻密さが伝わる。

4. **既存調査（③斬新さ・効果の土台）**  
   - 既存の医薬品推奨・OTC相談システム、LLMのみで推奨するサービス、ルールベースのみの事例を1～2段落で簡潔にまとめ、「だからLLMはNLUに限定し、推奨はルール＋潜在空間ハイブリッドで数理保証する」という流れをはっきりさせると、斬新さが伝わりやすい。

5. **デモ・二次審査**  
   - 本番環境（Render）のURLと、**デモ動画**（2～3分で「入力→推奨→根拠」が見えるもの）を用意しておくと、審査で有利。環境依存で手間がかかる実機デモより動画を推奨（竹内PMメッセージ⑤）。
