## 同時アクセス数の計算

### 基本計算式

#### 1. 同時処理数（ピーク時）

```
同時処理数 = ワーカー数
```

**現在の環境**:
- インスタンス1: 2ワーカー
- インスタンス2: 2ワーカー
- **合計**: 4ワーカー = **同時に4人のリクエストを処理可能**

#### 2. 1時間あたりの処理能力

```
1時間あたりの処理能力 = (3600秒 / 平均処理時間) × ワーカー数
```

**現在の環境での計算**:
- 平均処理時間: 27.5秒
- ワーカー数: 4
- 計算: (3600 / 27.5) × 4 = 130.9 × 4 = **約524リクエスト/時間**

#### 3. 1日あたりの処理能力

```
1日あたりの処理能力 = 1時間あたりの処理能力 × 24時間
```

**現在の環境での計算**:
- 1時間あたり: 524リクエスト
- 1日あたり: 524 × 24 = **約12,576リクエスト/日**

## ボトルネック分析

### 1. CPU制約

**現在の環境**:
- CPU: 0.5 per instance
- 合計: 1.0 CPU（2インスタンス）

**影響**:
- CPU集約的な処理（医薬品推奨）がボトルネック
- ワーカー数を増やすと、コンテキストスイッチのオーバーヘッドが増加

### 2. メモリ制約

**現在の環境**:
- RAM: 512MB per instance
- 合計: 1GB RAM（2インスタンス）

**影響**:
- 各ワーカーは約50-100MBのメモリを使用
- 4ワーカーで約200-400MB使用
- 安全マージン: 約100-300MB

### 3. 処理時間の制約

**現在の環境**:
- 平均処理時間: 27.5秒
- タイムアウト: 120秒

**影響**:
- 処理時間が長いため、同時処理数が制限される
- ワーカー数 = 同時処理数

### 4. データベース接続の制約

**現在の環境**:
- 接続プール: min 2, max 10 per instance
- 合計: min 4, max 20接続

**影響**:
- 通常は問題なし
- ピーク時は接続プールの上限に達する可能性

## スケーリング戦略

### 現在の構成での改善

#### 1. 処理時間の最適化

**目標**: 平均処理時間を20秒以下に短縮

**方法**:
- キャッシュの活用
- データベースクエリの最適化
- 非同期処理の導入（gevent）

**効果**:
- 1時間あたりの処理能力: 524 → 720リクエスト（約37%向上）

#### 2. ワーカー数の調整

**現在**: 2ワーカー per instance

**調整案**:
- メモリに余裕がある場合: 3ワーカー per instance（合計6ワーカー）
- ただし、CPU制約を考慮すると2が適切

### より大きなプランへのアップグレード

#### オプション1: より多くのCPU

**例**: 1 CPU per instance

**効果**:
- ワーカー数: 2 → 3 per instance（合計6ワーカー）
- 同時処理数: 4 → 6人
- 1時間あたりの処理能力: 524 → 786リクエスト（約50%向上）

#### オプション2: より多くのメモリ

**例**: 1GB RAM per instance

**効果**:
- ワーカー数: 2 → 4 per instance（合計8ワーカー）
- 同時処理数: 4 → 8人
- 1時間あたりの処理能力: 524 → 1,048リクエスト（約100%向上）

#### オプション3: インスタンス数の増加

**例**: 2 → 4インスタンス

**効果**:
- ワーカー数: 4 → 8ワーカー（2ワーカー per instance維持）
- 同時処理数: 4 → 8人
- 1時間あたりの処理能力: 524 → 1,048リクエスト（約100%向上）
