## 00結論

調査で分かった四点。うち二点は「やればできる」、二点は「先に決めないと手戻りする」。

01

#### 音声の入口と出口は、すでに動いている

音声入力（Web Speech API）も読み上げ（Web Speech / Polly Mizuki / Google ja-JP-Neural2-B、SSML 付き）も実装済みで、`POST /api/tts` が MP3 を返す。不足しているのは「顔のレンダリング」「割り込み」「会話のターン制御」の三つだけ。

#### 本当の壁は描画ではなく遅延

症状推奨フローは実測 p95 約 24 秒（KPI は 15 秒未満）。テキスト UI なら「処理中」表示で許される 24 秒も、人の顔が黙っていると故障に見える。アバターは沈黙の増幅器。

#### 「ビデオ通話風」は法的に踏んではいけない線の近く

2026 年 5 月 1 日施行の改正薬機法では、要指導医薬品のオンライン販売の条件が薬剤師によるビデオ通話等での情報提供。人の顔が話す UI は、この遠隔服薬指導と誤認されうる。AI である明示が機能要件になる。

#### フォトリアルは信頼を下げる側に働く

医療文脈の研究では、実写に寄せて作り込み切れないアバターは不気味の谷に落ち、信頼と視線を減らす。一方でカートゥーン調の人型は「親しみやすい・有効・不気味でない」と評価された。既存の Sage の世界観と方向が一致する。

## 02「バーチャルヒューマン」の三つの解釈

この言葉は少なくとも三つの別物を指します。どれを指しているかで、工数もコストも法務リスクも変わります。

 

三方式は、同じ既存パイプラインのどこに接続するかが違う。A は末尾に足すだけで本体に触れない。B は入口を差し替えて推奨生成を非同期に追いやる。C は応答テキストから映像そのものを外部生成する。テラコッタは第一段階として推奨する接続点。

### 方式 A — 読み上げアバター（Talking Head）

既存の `/api/tts` が返す音声に、クライアント側で口の動きを合わせるだけ。サーバーもパイプラインも無改造。「顔のある読み上げ」であって「対話」ではありませんが、体験の変化量に対して工数が圧倒的に小さい。技術は Live2D Cubism SDK for Web、`@pixiv/three-vrm` + `three-vrm-lip-sync`、TalkingHead.js のいずれか。

### 方式 B — リアルタイム対話（自前構成）

WebRTC／WebSocket で音声を双方向ストリーミングし、割り込み（barge-in）に対応する。OpenAI Realtime API（`gpt-realtime-mini`）が最短経路。アバター描画自体は A と共通なので追加描画コストはゼロ。ただし既存の推奨フローは 24 秒かかるので、リアルタイム化できるのは問診・雑談の層だけ。二層構成が前提になります（→ 第 3 章）。

### 方式 C — 商用リアルタイムアバター API

HeyGen LiveAvatar、Tavus、Simli、Anam、bitHuman など。映像そのものをクラウドで生成し WebRTC で配信する。実装は最速でフォトリアル。代償は従量課金（$0.009〜0.37/分）、日本語リップシンク品質の未検証、そして不気味の谷と肖像権。LiveKit Agents のアバタープラグイン層（14 社以上を同一インターフェースで抽象化）を噛ませれば、ベンダーの載せ替えは後から効きます。

## 03遅延という壁

この機能の成否を決める単一の数字。ここを設計しないと、どの方式を選んでも失敗します。

会話のターン交代は、言語を問わず平均 0.2 秒前後で起きます。1 秒を超える沈黙は「間」として意識され、数秒で気まずさに変わる。ところがこのアプリの症状推奨フローは——正確で安全である代わりに——桁が違います。

自然な対話として許容される沈黙（目安）約 1 秒

Physical E2E の KPI 目標 15 秒

Physical E2E の実測 p95約 24 秒

推奨処理の想定所要 25 – 30 秒

0 秒 10 20 30 秒

同一の線形スケール上での比較。KPI 目標の 15 秒ですら、自然な対話の 15 倍の沈黙にあたる。出典: `docs/dev/PHYSICAL_SYMPTOM_E2E.md`（p95・KPI）、`docs/planning/GCP移行計画.md`（推奨処理 25–30 秒）。

テキスト UI と人の顔では、同じ 24 秒の意味が違う。進捗ラベルが動いていれば、テキストチャットの 24 秒は「考え中」と読まれます。同じ 24 秒を人の顔が黙って過ごすと、読まれ方は「フリーズした」「聞こえていない」に変わる。アバターは体験の増幅器であり、遅い体験を載せれば遅さが増幅されます。

### 打ち手は三つ、併用が前提

- 二層化（本命） — 問診・相槌・確認のやりとりを「リアルタイム層（1.5 秒以内）」として分離し、推奨生成は裏で走らせる。アバターは問診を続けながら候補を待つ。会話として自然で、かつ既存の推奨品質に一切触らない。
- フィラー発話（即効性が高い） — 既存の `processing_user_labels.py` が持つフロー別ラベル群を音声化し、待ち時間に「いま候補を絞っていますね」と喋らせる。この資産がすでにあるのは大きい。沈黙を潰すだけで体感が変わります。
- 推奨フローの高速化 — 本質的な改善だが、バーチャルヒューマンとは独立した別課題。ここに依存させると着手できなくなります。

## 05法規制と倫理

この章が、技術選定より先に効きます。医薬品 × 人の顔 × 音声という組み合わせは、規制の線に近い。

### 改正薬機法（2026 年 5 月 1 日施行）との距離

今回の改正で、要指導医薬品のオンライン販売が解禁されました。ただし条件は「薬剤師がビデオ通話等を通じて情報提供・指導を行った場合に限る」であり、電話・メール・チャットでは販売できません（改正法 29 条の 5〜9）。緊急避妊薬等は「特定要指導医薬品」として対面販売義務が継続します。

ここから導かれる設計上の含意は一つです。ビデオ通話に似た見た目は、「薬剤師と話している」という誤認を生みうる。本アプリは診断も販売も行わない情報提供ツールであり、AI アバターは薬剤師の代替になりません。

設計要件として落とすなら。

① 画面上に常時「AI です／薬剤師・医師ではありません」を可視で表示する（免責文へのリンクではなく、アバターと同一視野に）。 ② 白衣・名札・薬局カウンター背景など、職能を想起させる意匠を避ける。 ③ 実在の人物に似せない（肖像権・パブリシティ権）。音声クローンを使うなら本人同意を書面化する。 ④ 会話が「買い方」に踏み込みやすくなるため、アバター経路も既存の `safety_gate` / `security_validator` を必ず通す。バイパス経路を作らない。

### 指定濫用防止医薬品との関係

同改正で新設された指定濫用防止医薬品（エフェドリン、コデイン、ジヒドロコデイン、ジフェンヒドラミン、デキストロメトルファン、プソイドエフェドリン、ブロモバレリル尿素、メチルエフェドリンの 8 成分）は、18 歳未満への大容量販売禁止・本人確認義務の対象です。親身に話すアバターほど、利用者は踏み込んだ質問をします。既存の安全網がアバター経路でも同じ強度で効くことを、実装前に確認してください。

### プライバシーポリシーの改定要否

現行のプライバシーポリシー第 2 条が列挙する取得情報に、音声データの記載がありません。以下の分岐で対応が変わります。

- ブラウザ内で完結（Web Speech API） — 音声波形はサーバーに届かない。現行条文のままで概ね整合。
- サーバー送信（Realtime API / クラウド transcribe） — 音声＝取得情報。第 2 条への追記と、保存する／しないの明示が必要。
- カメラ使用 — 顔画像は個人情報にあたり、要求水準が一段跳ね上がります。初期段階ではカメラなしを強く推奨。バーチャルヒューマン側が喋るだけなら、利用者を撮る理由はありません。

### ライセンスの整合

本リポジトリは PolyForm Noncommercial 1.0.0（非商用）。一方で改善方針 2026-09 には「商用化を視野」とあります。商用アバター API の利用規約・生成物の権利範囲は、商用化の判断時に再点検が要る項目として控えておくのが安全です。

## 06見た目の設計

「どこまで人間に似せるか」には、好みではなく研究の蓄積があります。

医療文脈の先行研究が示す傾向は、直感と逆です。ディープフェイク技術で生成したフォトリアルな人物像は「幽霊のよう」と評され不気味さを生んだ一方、限定的なアニメーションのカートゥーン調エージェントは「親しみやすく、有効で、不気味でない」と評価されました。実写に近づけて作り込み切れない領域では、信頼が下がり、視線が逸れ、ラポールが損なわれます。

同時に、バーチャルエージェントに対する患者の受容と信頼は総じて高く、バーチャル精神科問診の研究でも高い関与率が報告されています。そして——これが OTC 相談にとって本質的なのですが——人間相手より言いにくいことが言えるという自己開示の効果があります。恥ずかしさを伴う症状こそ市販薬相談の中核であることを考えると、ここがバーチャルヒューマンの最大の価値になりえます。

推奨する方向。既存の Sage の視覚言語（スレートブルー／テラコッタ／和紙調の落ち着き）に沿った、スタイライズドな 2D または 3D キャラクター。フォトリアルな人間は、技術的に可能であっても医療文脈では避ける。これは第 5 章の「薬剤師と誤認させない」要件とも同じ方向を向いています。

### アクセシビリティ

主要な利用者像に高齢者が含まれます（AWS コンテスト資料の地域課題分析より）。アバターは代替ではなく追加として設計してください——テキストは常に残す、字幕を併記する、アバターを完全に切れるトグルを置く、`prefers-reduced-motion` を尊重する。既存の「アクセシビリティ優先」UI パターン（`UI/patterns/10-accessibility-first.html`）の思想と揃えられます。

## 07段階導入案

各段階が単独で価値を出し、次に進まなくても無駄にならない構成にしています。

PHASE 0 1–2 週

#### 既存の読み上げに顔をつける（方式 A）

サーバー無改造。`/api/tts` の音声にクライアント側でリップシンクするキャラクターを重ねる。フィーチャーフラグ `AVATAR_ENABLED` で既存 UI と共存させ、いつでも落とせる状態にする。

- 追加コスト ¥0、遅延増加なし、既存パイプラインへの影響なし
- 測るもの: 読み上げ利用率、セッション継続率、離脱ポイントの変化

PHASE 1 2–4 週

#### 24 秒の沈黙を潰す

`processing_user_labels.py` のフロー別ラベルを音声化し、待ち時間にアバターが状況を語る。表情の切り替えも同じイベントに乗せる。既存の SSE 段階イベントがそのまま使えるので、新規の通信設計が要りません。

- 体感遅延の改善幅がもっとも大きい段階
- 測るもの: 推奨完了までの離脱率

PHASE 2 1–2 か月

#### 問診層だけリアルタイム化（方式 B）

`gpt-realtime-mini` で問診・確認・相槌を 1.5 秒以内に返す層を作り、推奨生成は従来どおり裏で走らせる二層構成。ここで初めて「対話」になります。

- 安全網の再確認が必須（音声経路が `safety_gate` を迂回しないこと）
- プライバシーポリシー第 2 条の改定がここで必要になる

#### 商用アバター API の PoC（方式 C）

コンテスト・デモの文脈に限定して検証。日本語リップシンク品質・コスト・法務の三点で本番採用を判断する。LiveKit Agents のプラグイン層を挟んでおけば、ベンダーの載せ替えコストを抑えられます。

- 常時稼働は月額が桁違いになる（→ 第 8 章）

## 09確認したいこと

ここから先は、決めていただかないと設計が分岐します。上の 4 つが特に効きます。

Q1「バーチャルヒューマン」はどの見た目を指していますか

スタイライズドな 2D / 3D キャラクター（Sage の擬人化）か、フォトリアルな人物か、あるいは実写ベースの AI 生成動画か。第 2 章の A / B / C はここで決まります。

Q2「対話」はどこまでを指していますか

既存の回答を顔つきで読み上げれば足りるのか、割り込み可能な音声会話（相手の話に被せて話せる）までを想定しているのか。工数が 1〜2 週と 1〜2 か月に分かれます。

Q3主目的は本番機能ですか、デモ・コンテストですか

AWS 地域創生コンテストや技育祭の資料が揃っているため、直近のデモ映えが目的なら方式 C の短期 PoC、長期の本番機能なら方式 A からの積み上げと、最適解が反転します。

Q4追加の月額予算はどの程度まで許容できますか

¥0（方式 A 一択）／月 1 万円台（方式 B が入る）／月 10 万円以上（方式 C が入る）で、選べる技術が変わります。

Q5対象チャネルは Web だけですか

LINE にもアバターを出したいか。LINE は動画・音声メッセージの制約が別物で、リアルタイム対話は事実上できません。店頭キオスク設置の構想があるなら、また別の設計になります。

Q6利用者のカメラを使う想定はありますか

顔を撮らないなら個人情報の扱いが大きく軽くなります。現時点では「使わない」を推奨しますが、視線や表情から体調を読む構想があるなら、法務要件を先に固める必要があります。

Q7キャラクターの造形・声はどう調達しますか

自作、外注、VRoid 等の既製モデル、商用アバター API の既製アバターのいずれか。声も、既存の Google / Polly の合成音を続けるのか、キャラクター性のある声（にじボイス等）に差し替えるのか。「Sage」に顔と声を与えるという意思決定そのものが、まだリポジトリのどこにも存在しません。

Q8多言語（英語・中国語・韓国語）も対象ですか

既存の TTS は 4 言語に対応済みですが、リップシンクの音素マッピングは言語ごとに要調整です。インバウンド観光客対応が狙いなら、初期から設計に入れる必要があります。

Q9成功をどう測りますか

継続率か、相談完了率か、言いにくい症状の開示率か、デモでの反応か。Phase 0 の効果測定をどこに置くかが決まります。

Q10いつまでに何が要りますか
