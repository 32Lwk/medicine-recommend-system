## 00 3 件を突き合わせて分かったこと

単体では見えず、重ねて初めて見えた 7 点。以降のロードマップの変更はすべてここから導いている。R2 の主要指摘（H1・H2・H8・T1）は 2026-09-14 時点の HEAD で再確認済み。

1. 「Phase 0 ではコードに触れない」という前提が成立しない

初版の Phase 0 は認証・レート制限・ログ管理という運用項目だけで構成し、コード修正を意図的に外していた。しかし R2 は、公開の可否以前に現在進行形で誤っている不具合を 2 件実証している。

R2 H1 年齢制限欄の「1回量」の `1` を最小年齢として拾い、10 歳のユーザーに「15才未満：服用しないこと」の解熱鎮痛薬を推奨する（CSV 7,495 行中 1,941 行が同じ過小抽出）。 R2 H2 成分名を正規表現として pandas に渡すため、胃腸症状の相談が例外停止して推奨が一切出ない（本番ログに発生実績）。どちらも修正は数行。Phase 0 に「構造に触れない安全修正」の枠を設けた。
2. Phase 2 の完了条件が空手形だった

初版は巨大関数の分解を「ゴールデン回帰が完全一致」でマージする設計だった。ところが R2 T1 によれば、`test_golden_regression.py` は `rule_based_medicine_recommendation` 自体をモックし期待値リストは空、`test_menstrual_recommendations.py`（15 件）は結果キー名の誤り（`recommendations` / 実際は `recommended_medicines`）で常に空リストを見ており assert が無いため必ず pass、そして CI（GitLab・GitHub とも）は `tests/core` を実行していない。

スコアリングの回帰網は現在存在しない。分解に着手する前ではなく、Phase 0 のスコア修正に着手する前に、最小限のスナップショットが要る。
3. C8（製品名ハードコード）の被害が実証され、P4-1 を前倒しできる

`改善計画.md` 2.2 の「頭痛時にカロナールを第一選択にしたいがイブプロフェン系が上位に来る」の直接原因は R2 H5。`MAJOR_ANALGESIC_MEDICINES` の `'イブ'` が部分一致で使われ、CSV の 81 製品が「主要解熱鎮痛薬」扱いになる。うち 49 製品は目薬・鼻炎薬・風邪薬・外用薬（例: なみだロートファイブ、キッズバファリン鼻炎シロップ）。同じく 2.3「2位・3位に同成分を並べない」は R2 M7（包装違い・剤形違いの重複）。

初版で Phase 4（9か月〜）に置いた推奨品質の改善は、Phase 1 の H5・M7 修正でその大半が片付く。
4. C4 と R2 M11 は同じ対象で、実害の範囲が確定した

`enhanced_safety_checker._should_use_strict_weights` のコールスタック検査について、R2 は現行デプロイ（`.env.example` / `render.yaml` / `cloudbuild` / `buildspec` のいずれにも該当変数なし）では発火せず重みが 0.10 / 0.05 のままであることを実測確認している。つまり緊急ではない。一方で strict が有効な場合は重みが負に反転し副作用が大きいほど加点になることも判明した。P1-2 は「削除」で正しいが、単純削除ではなく符号の是正を伴う。
5. R3 は、ロードマップにタスクが存在しない領域を一つ明るみに出した

推奨フローは実測 p95 約 24 秒（`docs/dev/PHYSICAL_SYMPTOM_E2E.md` の KPI は 15 秒未満）。初版のロードマップには性能改善の項目が Phase 0〜4 のどこにも無い。テキスト UI では進捗ラベルが「考え中」と読ませるため成立しているが、人の顔が黙って 24 秒過ごすと「故障した」と読まれる。バーチャルヒューマンに進むなら性能は前提条件になる。

なお R2 M5 は、簡易スコアの選別が定数表のボーナスを反映しない品質問題であると同時に、本番ログで 1,737 件を詳細採点している性能問題でもある（品質と性能の両方に効く唯一のタスク）。
6. 公開前タスクと VH の法務要件が地続き

P0-6（ライセンス・権利整理）は商用アバター API の利用規約と生成物の権利範囲を含められる。P0-5 / P3-5（秘密情報と PII 方針）は、現行プライバシーポリシー第 2 条に音声データの記載が無いという R3 の指摘とそのまま重なる。VH に進む可能性があるなら、同じ棚卸しの中で一度に片付けるほうが手戻りが少ない。
7. 安全網の一元化（Phase 1）は VH の着手条件でもある

2026-05-01 施行の改正薬機法は、要指導医薬品のオンライン販売条件を「薬剤師がビデオ通話等で情報提供・指導を行った場合」と定める。人の顔が話す UI はこの遠隔服薬指導と誤認されうるため、AI である明示が機能要件になる。加えて指定濫用防止医薬品 8 成分の新設により、親身に話すアバターほど踏み込んだ質問を引き出す。禁忌ルールの正本が 2 箇所にある状態（C3）のままチャネルを増やすのは順序が逆。

## 01システムの目的と現在地

症状を自然言語で入力すると市販薬（OTC）候補を提示し、注意点と受診目安を案内するチャット型相談ツール。医療行為の代替ではなく、セルフメディケーションの補助が目的。Web（SSE ストリーミング）と LINE の2チャネルを持ち、専門関係者向けの限定 β として運用中。

推奨の主軸

ルールベース採点。ただし R2 の実測では主要入力で 16〜22 製品が同一の最大値 `1.3629` に飽和し、上位 3 件は実質 CSV の並び順と製品名ベースの後段規則で決まっている

LLM の用途

トリアージ、症状 NLU のフォールバック、説明文・Q&A・カウンセリング生成、意図ルーティング

RAG

ローカル BM25 + 埋め込み（本番）、Bedrock Managed KB（AWS ステージングのみ）

配備

GCP Cloud Run（本番・dev）、AWS ECS Fargate（ステージング、通常停止）、Render 設定は残骸

規模

src 約11万行、テスト 411 ファイル、コミット 1,100 件（2025-10〜2026-08）

応答性能

Physical E2E 実測 p95 約 24 秒（KPI 15 秒未満）。担当タスクは未設定だった → P4-6 を新設

音声

入力（Web Speech API）・出力（Web Speech / Polly Mizuki / Google ja-JP-Neural2-B、SSML 調整済み）とも実装済み。`POST /api/tts` が MP3 を返す

ライセンス

PolyForm Noncommercial 1.0.0。商用化時は見直しが必要

## 04改善の基本方針

1. 安全性の正本を一つにする。 禁忌・年齢・妊娠・相互作用のルールはデータ（JSON/CSV）として一元管理し、コードはそれを読むだけにする。薬剤師等の専門家レビューを受けられる形式にする。
2. 直す前に計測の網を張る。（R2 を受けて追加）スコアリングは現在、回帰を検出する手段が無い。代表入力の上位 3 件をスナップショットで固定してから修正に入る。特に C20・C21 を直すと C19 の飽和が表面化するため、この 3 件は一括で扱い前後比較する。
3. v2 ルーティングへ一本化し、旧経路と関連フラグを削除する。 判断経路は「ゲート → LLM → ガード → ディスパッチ」の一本に固定し、セッション内の状態は型付きオブジェクトにまとめる。
4. 巨大関数を「ステージ関数 + 明示的な状態オブジェクト」へ分解する。 挙動を変えずに切り出し、ゴールデン・E2E コーパスを回帰の網にする（ただしその網は §5 Phase 0-1 で先に作る）。
5. 本番運用の前提を公開向けに引き上げる。 認証、レート制限、監査ログ、PII 取り扱い、ログ保管先の分離、依存更新の仕組みを整える。
6. リポジトリを軽く、境界を明確にする。 ログ・大容量アーカイブ・画像は外へ出し、`src/services/` をパッケージ化し、評価ツールは `tools/` へ分離する。
7. 一度に一領域。 個人開発なので並行改修はせず、各フェーズで完了条件を満たしてから次に進む。バーチャルヒューマン（§6）はこの原則の例外にあたるため、着手条件を明示した。

## 06機能トラック: バーチャルヒューマン（R3）

改善ロードマップとは別トラック。§4 の原則 7「一度に一領域」の例外にあたるため、どの段階にどの前提が必要かを明示する。

### 6.1 調査の要点

- 音声の入口と出口はすでに動いている。 入力（Web Speech API）も読み上げ（Web Speech / Polly `Mizuki` / Google `ja-JP-Neural2-B`、SSML で文末 450ms の間・話速 94% まで調整済み）も実装済みで、`POST /api/tts` が MP3 を返す。不足しているのは「顔のレンダリング」「割り込み」「ターン制御」の 3 つだけ。ゼロからの音声対話システム構築ではなく、既存の音声パイプラインに顔と間（ま）を足す作業として設計できる。
- 本当の壁は描画ではなく遅延。 会話のターン交代は平均 0.2 秒前後で起き、1 秒を超える沈黙は「間」として意識される。対して推奨フローは p95 約 24 秒（C25）。テキスト UI の 24 秒は「考え中」と読まれるが、人の顔が黙った 24 秒は「故障」と読まれる。アバターは体験の増幅器。
- フォトリアルは信頼を下げる側に働く。 医療文脈の研究では、実写に寄せて作り込み切れないアバターは不気味の谷に落ち信頼と視線を減らす一方、カートゥーン調の人型は「親しみやすい・有効・不気味でない」と評価された。既存の Sage の視覚言語（スレートブルー `#5b7c99` ／ テラコッタ `#c9846a`）と方向が一致する。
- 自己開示の効果がこのアプリに固有の価値になりうる。 バーチャルエージェント相手だと人間相手より言いにくいことが言えるという研究がある。恥ずかしさを伴う症状が OTC 相談の中核であることを考えると、ここが最大の便益。

### 6.2 三方式と単価（2026-09 時点、$1 = ¥150）

### 6.4 全段階に共通する設計要件（法務・倫理）

改正薬機法（2026-05-01 施行）は、要指導医薬品のオンライン販売条件を「薬剤師がビデオ通話等で情報提供・指導を行った場合に限る」と定める（改正法 29 条の 5〜9）。本アプリは診断も販売も行わない情報提供ツールであり、AI アバターは薬剤師の代替にならない。人の顔が話す UI はこの遠隔服薬指導と誤認されうるため、以下は機能要件として扱う。

1. 画面上に常時「AI です／薬剤師・医師ではありません」を可視表示する（免責文へのリンクではなく、アバターと同一視野に）。
2. 白衣・名札・薬局カウンター背景など、職能を想起させる意匠を避ける。
3. 実在の人物に似せない（肖像権・パブリシティ権）。音声クローンを使うなら本人同意を書面化する。
4. アバター経路も既存の `safety_gate` / `security_validator` を必ず通す。バイパス経路を作らない。指定濫用防止医薬品 8 成分（エフェドリン、コデイン、ジヒドロコデイン、ジフェンヒドラミン、デキストロメトルファン、プソイドエフェドリン、ブロモバレリル尿素、メチルエフェドリン）は 18 歳未満への大容量販売禁止・本人確認義務の対象であり、親身に話すアバターほど利用者は踏み込んだ質問をする。
5. 初期段階ではカメラを使わない。顔画像は個人情報にあたり要求水準が一段上がる。アバターが喋るだけなら利用者を撮る理由がない。
6. アクセシビリティ: アバターは代替ではなく追加。テキストは常に残す、字幕を併記する、完全に切れるトグルを置く、`prefers-reduced-motion` を尊重する（既存の `UI/patterns/10-accessibility-first.html` の思想と揃う）。
7. 見た目は Sage の視覚言語に沿ったスタイライズドな 2D / 3D。フォトリアルは技術的に可能でも医療文脈では避ける（§6.1・要件 1 と同じ方向）。

## 07進め方の補足

回帰ゲート: ゴールデン回帰、Tier1 短文、Physical 10、GPT ペルソナ（targeted）、契約テスト、および P0-7 のスコアスナップショット。Phase 2 以降の分解作業は「テスト全 PASS かつ採点結果が完全一致」を条件にマージする。

スコア修正の順序（統合による追加）: `H3`（C20）と `H4`（C21）を直すと症状適合度・効能特異性が全体的に変化し、`H6`（C19）の飽和が表面化する。この 3 件は一括で扱い、スナップショットで前後比較する。単独で直すと順位が壊れたように見える。

フラグ削減の順序: 旧経路削除 → v2 サブフラグ削除 → `RECO_*` を既定 ON に固定して削除 → UX Phase フラグ整理。1 か月本番で問題がなければ次を消す。

ドキュメント: 変更ごとに `ARCHITECTURE_MULTI_AGENT.md` / `CHAT_PIPELINE_V2.md` / `ROUTE_SPEC.md` を更新。CHANGELOG は要点のみにし、詳細は PR に寄せて肥大化を止める。

テスト環境: ローカルに Python 3.11 が無い（システムは 3.9、コードは `X | None` 構文を使用）。`python:3.11-slim` コンテナで実行する。

リスク: 個人開発のため Phase 2 の分解中に機能追加が入ると衝突する。分解中は機能追加を止める期間を決めるとよい。バーチャルヒューマン（§6）は VH-0・VH-1 なら Phase 0–1 と並行しても衝突しにくいが、VH-2 以降は Phase 2 の分解と重ねない。

### B. 運用

4. AWS ステージングの位置づけ: コンテスト後も Bedrock KB の実験場として維持するか、費用最小化のため閉じるか。
5. ログの保管先: GCS と S3 のどちらを正とするか。既存の解析スクリプトは双方に export があるため、一本化先の希望があるか。
6. 旧 API の利用者: `/api/main_*`、`/test/*` ミラー、`LEGACY_UI_FALLBACK` を使う外部クライアントや検証者はいるか。いなければ Phase 3 で削除する。

### C. 推奨の仕様（R2 により新たに判断が必要になった点）

7. 「必ず 3 件出す」を維持するか: `H7` の無条件再追加は 3 件保証のために存在する。安全フィルタを尊重すると、候補が足りない場合に 0〜2 件で返すことになる。これは製品判断。
8. `final_score = 0` の候補を出すか: 現状は「便秘がつらい」の 3 件全てが score 0・表示 42.5%・レベル「中」で出ている（`M1`）。出さない／「参考候補」と明示する／現状維持のいずれか。
9. 到達不能だった漢方の症状別調整を有効化するか: `H10` の修正で、これまで一度も適用されていなかった調整値（葛根湯の単一症状 −0.30〜−0.60 等）が初めて効き始める。値そのものを専門家レビュー前に有効化するかは判断が要る。

### D. バーチャルヒューマン（R3 の Q1–Q10 を圧縮）

10. どの見た目で、どこまでの「対話」か: スタイライズドな 2D/3D キャラクター（Sage の擬人化）か、フォトリアルか。既存回答を顔つきで読み上げれば足りるのか、割り込み可能な音声会話までを想定しているのか。工数が 1–2 週と 1–2 か月に分かれる。
11. 本番機能かデモか、追加月額の上限はいくらか: 直近のデモ映えが目的なら方式 C の短期 PoC、長期の本番機能なら方式 A からの積み上げと、最適解が反転する。¥0 / 月 1 万円台 / 月 10 万円以上で選べる技術が変わる。
12. 対象チャネル・キャラクター調達・多言語: Web だけか（LINE はリアルタイム対話が事実上できない。店頭キオスク構想があるとまた別の設計）。造形と声は自作・外注・既製モデル・商用 API のどれか。en/ko/zh のリップシンク音素マッピングを初期から設計に入れるか。「Sage」に顔と声を与えるという意思決定そのものが、まだリポジトリのどこにも存在しない。
