# Render から AWS / GCP 等への移行比較

**目的**: より低額で運用維持可能・高性能なクラウドへの移行検討  
**前提**: 現状は Render（Web Service + 必要に応じて DB）、Flask + Gunicorn、PostgreSQL、長時間リクエスト（推奨処理 25–30 秒、タイムアウト 120 秒）

---

## 1. Render のメリット（現状の強み）

| 項目 | 内容 |
|------|------|
| **運用の手軽さ** | Git 連携で push だけでデプロイ。Docker 不要で Python ビルド＋start コマンドだけで稼働。 |
| **設定の一元化** | `render.yaml` でサービス定義をコード管理でき、再現性が高い。 |
| **マネージド DB** | Render PostgreSQL を同じダッシュボードで追加・管理しやすい。 |
| **コストの予測しやすさ** | プラン単価が明確（Starter $7/月〜、その上はインスタンス単価）。 |
| **学習コスト** | AWS/GCP より概念が少なく、小規模チームでも運用しやすい。 |

**注意点**: 本番で安定・高性能を求める場合はインスタンスを上げる必要があり、その分コストが増えやすい。低予算でスケールさせると Render の単価は相対的に高くなることがある。

---

## 2. 候補プラットフォーム一覧

| プラットフォーム | 形態 | 主な特徴 |
|------------------|------|----------|
| **GCP Cloud Run** | コンテナ・サーバーレス | リクエスト時課金・スケールゼロ・長時間対応可能 |
| **AWS App Runner** | コンテナ・マネージド | GitHub 連携・Python 直接対応・常時起動も可能 |
| **AWS ECS Fargate** | コンテナ・オーケストレーション | 細かいリソース指定・Spot でコスト削減 |
| **AWS Lightsail** | 小型 VM / コンテナ | 固定料金・シンプル・小規模向け |
| **Fly.io** | コンテナ・エッジ | 秒単位課金・リージョン選択・低レイテンシ |
| **Railway** | PaaS | 使用量課金・Render に近い UX |
| **DigitalOcean App Platform** | PaaS | シンプルな料金・マネージド DB 連携 |

---

## 3. 各プラットフォームの概要・メリット・コスト・移行難易度

### 3.1 GCP Cloud Run

**メリット**
- **従量課金**: リクエスト処理中のみ vCPU・メモリを課金。アイドル時はほぼゼロ。
- **長時間リクエスト**: リクエストタイムアウトを最大 60 分まで設定可能（本アプリの 120 秒も余裕で対応）。
- **スケールゼロ**: トラフィックがなければインスタンス 0 になり、その間のコストがかからない。
- **無料枠**: 月あたり 200 万リクエスト、36 万 vCPU 秒、18 万 GiB 秒などが無料枠。新規は $300 クレジットあり。
- **運用**: コンテナを渡すだけなので、一度 Docker 化すれば GKE などへの移行も容易。

**運用コスト（目安）**
- 軽いトラフィック（月 1 万リクエスト、1 リクエスト 30 秒・0.5 vCPU・512 MiB）: 無料枠内に収まる可能性が高い。
- 中程度（月 10 万リクエスト・同スペック）: おおよそ **$5–15/月** 程度（リージョン・実使用量による）。
- 常時ウォームにしたい場合は「最小インスタンス数 1」で常時 1 インスタンス起動となり、その分 24 時間課金。

**移行難易度: 中**
- **必須**: Dockerfile の作成、`PORT`（デフォルト 8080）で listen、ステートレス化（セッションは DB 等に寄せる＝現状に近い）。
- **既に合致している点**: セッションは DB 保存、環境変数で設定しているため、コンテナ化しやすい。
- **追加作業**: Cloud Build または GitHub 連携の CI/CD、Cloud SQL（PostgreSQL）の利用設定、Secret Manager で API キー管理。

**維持コスト**: 低〜中。マネージドなのでパッチ適用・OS 管理は不要。監視は Cloud Monitoring で可能。

---

### 3.2 AWS App Runner

**メリット**
- **GitHub 連携**: リポジトリ指定で自動ビルド・デプロイ。Render に近い体験。
- **Python 直接対応**: ソースからビルドできるため、Docker なしでも移行可能（推奨は Docker で再現性を上げる）。
- **マネージド**: ロードバランサー・スケール・デプロイを AWS が担当。
- **常時起動**: インスタンスを常時 1 以上にすればコールドスタートを避けられる（本アプリの 25–30 秒処理に有利）。

**運用コスト（目安）**
- Provisioned: 約 $0.007/GB-hour（アイドル時）、Active: 約 $0.064/vCPU-hour + $0.007/GB-hour。
- 常時 1 インスタンス（0.25 vCPU, 0.5 GB）: おおよそ **$15–25/月** 前後（ build 料金等含む）。
- トラフィックが少ない場合は「オートスケールで 0 に近づける」設定はできないため、常時起動だと Render と同程度〜やや高くなる場合あり。

**移行難易度: 低〜中**
- `render.yaml` の代わりに `apprunner.yaml` またはコンソールでソース・ビルド・起動コマンドを指定。
- 環境変数・シークレットは App Runner の設定または Secrets Manager で移行。
- RDS（PostgreSQL）は別途作成し、`DATABASE_URL` を渡す形で現状と同様に利用可能。

**維持コスト**: 低。オペレーションは Render と同程度で、AWS の監視（CloudWatch）を利用可能。

---

### 3.3 AWS ECS Fargate

**メリット**
- **きめ細かいリソース指定**: vCPU・メモリを 0.25 刻みで指定可能。本アプリの 512 MB・0.5 CPU に合わせやすい。
- **Spot**: 割り込み許容なら Spot で最大約 70% 割引が期待できる（バックグラウンド処理向け。Web は通常オンデマンド）。
- **スケール**: タスク数・オートスケールを自分で設計できる。
- **コスト最適化**: 使った分だけ課金。夜間トラフィックが少ない場合は深夜のコストが下がる。

**運用コスト（目安）**
- 0.25 vCPU, 0.5 GB のタスクを 1 つ 24 時間: おおよそ **$10–15/月**（リージョンによる）。
- ALB・ログ・データ転送を足すと **$15–25/月** 程度になることが多い。Render の Starter 複数インスタンスより安くなる場合あり。

**移行難易度: 高**
- VPC・サブネット・ALB・ECS クラスタ・タスク定義・サービス・IAM・ログなど、構成要素が多い。
- Dockerfile は必須。CI/CD は CodePipeline / GitHub Actions 等で自作。
- 運用・監視の知識が必要で、初期学習コストは高い。

**維持コスト**: 中〜高。インフラの変更・証明書更新・スケールポリシーの見直しなどを自分で行う必要がある。

---

### 3.4 AWS Lightsail

**メリット**
- **固定料金**: コンテナまたは小型 VM が月額 $7〜 など、分かりやすい価格。
- **シンプル**: EC2/ECS より設定項目が少なく、小規模サービス向け。
- **データベース**: Lightsail の PostgreSQL を同じ画面で追加しやすい。

**運用コスト（目安）**
- コンテナ $7/月〜、$10・$20 などのプラン。VM も同様の価格帯。
- **$7–20/月** で収まる構成が取りやすい。Render と同程度〜やや安くできる。

**移行難易度: 低〜中**
- Docker イメージを push するか、Git からビルドする形。`start.sh` 相当をコンテナの CMD にすればよい。
- 環境変数・DB 接続は Lightsail の画面または .env で設定。

**維持コスト**: 低。OS のアップデートは自分で行うが、Lightsail はパッチ適用が比較的簡単。

---

### 3.5 Fly.io

**メリット**
- **秒単位課金**: 使った分だけ。スケールゼロも可能（オプション）。
- **リージョン**: 複数リージョンにデプロイしてレイテンシを下げられる。
- **パフォーマンス**: 小さい VM を細かく割り当てられる。
- **開発者向け**: CLI が強力で、ローカルに近い体験でデバッグしやすい。

**運用コスト（目安）**
- 共有 CPU・256 MB の VM を 1 台常時: おおよそ **$5–10/月** 前後。
- トラフィックとスケールに応じて **$10–30/月** 程度まで変動しうる。

**移行難易度: 中**
- `fly.toml` と Dockerfile を用意。`PORT` は 8080 など Fly の指定に合わせる。
- PostgreSQL は Fly Postgres または外部（Supabase、Neon 等）を推奨。

**維持コスト**: 低〜中。プラットフォームがマネージドなので、アプリと設定の更新が中心。

---

### 3.6 Railway

**メリット**
- **Render に近い UX**: GitHub 連携、環境変数、ログが分かりやすい。
- **使用量課金**: 使った分だけなので、トラフィックが少ない月は安く収まりやすい。
- **PostgreSQL**: アドオンで簡単に追加可能。

**運用コスト（目安）**
- 無料枠 $5 クレジット/月。超過後は **$5–30/月** 程度になることが多い（リソース・トラフィック次第）。

**移行難易度: 低**
- Render とほぼ同様。`render.yaml` の代わりに Railway の「Build / Start」を設定。Docker は任意。

**維持コスト**: 低。Render からの移行負荷が最も小さい選択肢の一つ。

---

### 3.7 DigitalOcean App Platform

**メリット**
- **分かりやすい料金**: コンテナ・VM が月額 $5〜 など。
- **マネージド DB**: PostgreSQL を App Platform と一緒に管理できる。
- **シンプル**: AWS/GCP より概念が少ない。

**運用コスト（目安）**
- Basic コンテナ $5/月〜。DB を足すと **$15–30/月** 程度。

**移行難易度: 低〜中**
- Git または Docker でデプロイ。環境変数・DB 接続は画面で設定。

**維持コスト**: 低。

## 5. 推奨の選び方

- **「できるだけ安く、移行も楽に」**: **Railway** または **Fly.io**。Render と似た運用で、使用量に応じて $5–20/月 程度に収めやすい。
- **「将来的なスケールとコスト最適化を両立したい」**: **GCP Cloud Run**。Docker 化と CI/CD の一手間はあるが、従量課金・スケールゼロ・長時間リクエスト対応で、低〜中トラフィックでは非常にコスト効率が良い。
- **「AWS に寄せたい・マネージドで楽」**: **AWS App Runner**。GitHub 連携で Render に近い。常時起動にすると Render と同程度のコストになりやすい。
- **「AWS でコストを細かく最適化したい・インフラを自分で握りたい」**: **ECS Fargate**。初期構築は重いが、リソース・Spot の活用で長期的にコストを抑えられる。
- **「固定料金で分かりやすく」**: **Lightsail** または **DigitalOcean App Platform**。$7–20/月 で運用しやすい。

## 6. 移行時の共通作業（本アプリの場合）

1. **Docker 化（Cloud Run / ECS / Fly / App Runner のコンテナ利用時）**
   - `Dockerfile`: Python 3.11、`requirements.txt` で `pip install`、`start.sh` または直接 `gunicorn`。`PORT` は 8080（Cloud Run）または環境変数に合わせる。
   - `.dockerignore` で `data/` やキャッシュを除外し、ビルドを軽くする。

2. **データベース**
   - Render PostgreSQL から移行する場合はダンプ＆リストア、または Cloud SQL / RDS / 外部 PostgreSQL（Neon、Supabase 等）を新規作成し、`DATABASE_URL` を切り替える。

3. **シークレット**
   - `OPENAI_API_KEY`、`DEEPL_API_KEY`、`SECRET_KEY`、`DATABASE_URL` 等を各クラウドのシークレット管理（Cloud Run: Secret Manager、AWS: Secrets Manager / 環境変数）に移行。

4. **ヘルスチェック・タイムアウト**
   - 本アプリは 120 秒タイムアウトが必要。各プラットフォームで「リクエストタイムアウト」「ヘルスチェック間隔」を 120 秒以上に設定する。

5. **静的ファイル・アセット**
   - 現状は Flask で配信している想定。そのままでも動くが、将来 CDN（CloudFront、Cloud CDN）を前に置くとコスト・パフォーマンス両面で有利。
