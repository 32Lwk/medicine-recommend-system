# 提案書（proposal.tex）審査員視点・辛口評価と改善案

公募要領（koubo.md）および竹内統括PMメッセージ（竹内PM.md）を基準に、`proposal.tex` を審査員の立場から辛口に評価し、各項目ごとに批判的指摘と改善案を記載する。

---

## 1. 総合評価（辛口）

- **採択・不採択の境界線上にいる印象**。要件（25歳未満、独創性、世の中への出し方、計画の緻密さ）はおおむね満たしているが、「突出した人材」と「独創的なアイデア」の両方で、審査員が「これはつまみ上げたい」と強く思う一押しがやや弱い。
- **医療・医薬品**というドメインは、審査員が**責任・安全性・説明可能性**を厳しく見る分野である。5層防御やルール＋潜在空間の設計は書かれているが、「なぜその組み合わせが医療現場で受け入れられるか」の論理がもう一歩欲しい。
- **既存システムの延長**（「潜在空間を足す」）に読まれやすく、未踏が求める**ゼロから切り開く独創性**より**実装力・継続開発**の印象が強い。既存サービスを自分で作り上げたことは強みだが、未踏で「何を新規に創るか」を冒頭で一言で言い切れていない。
- **ページ数**：公募要領は「10ページ以内」と明記している。図表が多いため、PDFが10ページを超えている可能性がある。超えている場合は**審査対象外**のリスクがあるので要確認。

## 2. 項目別の批判的指摘と改善案

### ① 何を作るか

| 批判的指摘 | 改善案・どうすべきか |
|------------|----------------------|
| **背景が長く、自分史（和歌山・登録販売者・相談業務）に寄りすぎている。** 竹内PMは「長すぎる自分史はほとんど必要ありません」と明言している。 | 背景は**1段落に圧縮**し、「誰の・どんな課題か」と「本提案でどこまで作るか」を冒頭で一言で言い切る。自分史は2〜3行に凝縮し、**課題認識の根拠**としてだけ残す。 |
| 目的・目標と「システム概要」「5層防御」「医薬品推奨の流れ」は書けているが、**専門家でない人に伝わるかは図に依存**している。文章だけでも「入力→何を守るか→出力」が追えるようにする必要がある。 | ①の冒頭に**1〜2文の要約**を置く（例：「相談内容を入力すると、ルールとAIの二段構えで安全にOTC医薬品を推奨し、根拠を表示するシステムである」）。そのうえで図で補足する。 |
| 「潜在空間」が何であり、なぜ既存のLLM直接利用では不十分なのかが、①の段階ではやや分かりにくい。 | 目的の直後に「LLMは自然言語理解に限定し、推奨はルール＋潜在空間で行う理由」を1〜2文で書く。または③の斬新さで触れるなら、①では「推奨エンジンはルールと潜在空間を組み合わせる」とだけ明記し、③で詳述する。 |
| フローチャートと5層防御・パイプライン(1)〜(9)の**対応関係**が、文章では必ずしも明瞭でない。 | フローチャートの各ブロックに「対応する防御層（例：Layer 2）」をラベルするか、または「フローチャートの〇〇の段階で、5層防御のLayer 2が働く」と短い対応表または1文を入れる。 |

### ② どんな出し方を考えているか

| 批判的指摘 | 改善案・どうすべきか |
|------------|----------------------|
| **短期・中期・長期とビジネス3段階が並列**で、未踏の「事業化は第一義ではない」「世の中への出し方・問い方」とのバランスが曖昧。B2B・B2Gでエンドユーザー無料は、審査員に「絵に描いた餅」に見える可能性がある。 | **順序をはっきりさせる**。「第一に、広く使ってもらう（無料公開・オープンソース等）。その一形態として、修了後にSaaS・B2Bを検討する」と書き、ビジネス記述は「意図の例」として短くまとめる。 |
| 「4言語対応」は出し方の**差別化要因**だが、なぜ4言語か（在留・訪日・多言語ニーズ）の一文があると、審査員に伝わる。 | 4言語にした理由を1文追加する（例：在留外国人・訪日需要・将来的な東南アジア展開を見据えて）。 |
| ビジネスモデル図がある一方で、**収益化より普及・社会貢献が先**であることを、公募の趣旨に合わせて一言でいいので書く。 | 「未踏期間中は収益化より、利用拡大とフィードバック収集を優先する」のような1文を入れる。 |

### ③ 斬新さの主張、期待される効果など

| 批判的指摘 | 改善案・どうすべきか |
|------------|----------------------|
| **「LLMをNLUに限定し、推奨はルール＋潜在空間」**は、近年のRAG・ハイブリッド系ではよくある設計。**既存調査（Ubie、YOJO等）との差別化**が表だけで、なぜそのポジションで「突出」しているかの**因果の論理**が弱い。 | 既存研究・製品の**不足を1文ずつ**指摘し、「本提案は〇〇をしているから〇〇である」と**因果で書く**。ポジショニング図のキャプションで「差別化の理由」を1〜2文補足する。 |
| **99%・100%**などの数値の**根拠**（何のデータ・何の指標で測るか）が不明。審査員は「根拠のない数字」に厳しい。 | 評価指標の**算出方法**（使用するデータセット・検証方法・分母の定義）を簡潔に追記する。達成率は「目安」であれば「目標値（目安）」と明記する。 |
| オンボーディング画面は**斬新さ・UXの差別化**として有効だが、技術的裏付け（既存研究やプロトタイプ）とのつながりが薄い。 | オンボーディングを「初回利用時の理解を促し、誤用を防ぐ」という**安全性・5層防御**の一環として位置づけ、1文で技術的意図を書く。 |
| 期待効果がやや**一般的**。「薬機法・ガイドライン遵守」は必須条件であり、それを超えた**社会的インパクト**（例：相談の質の向上、多言語アクセス）を短くはっきり書く。 | 「相談の質の向上」「多言語での公平なアクセス」「将来の規制・ガイドライン変更への対応しやすさ」など、1〜2文で具体的に書く。 |

### ④ 具体的な進め方と予算

| 批判的指摘 | 改善案・どうすべきか |
|------------|----------------------|
| **平日178日・土日祝86日と「按分」で1,295時間**とあるが、**按分の計算式が書かれておらず検証できない**。審査は「計画の緻密さ」を見るため、数字の根拠が重要。 | **試験期・夏休み期・通常期の日数と1日あたり時間**を表で示し、合計が1,295時間になることを**式または表で明示**する。例：通常期○日×○h＋夏休み期○日×○h＋…＝1,295。 |
| **専門家監修**が「年4～6回」と「8月後半～12月末で定期的に依頼」の**関係が曖昧**。いつ・どの成果物に対して監修を受けるかが分かると信頼性が増す。 | 監修の**タイミング**（例：Phase 2/4/6 完了時、または○月・○月）と**回数**を一致させて記載する。「Phase完了時に監修を依頼し、年4〜6回を想定」など。 |
| **開発線表**と**フローチャート・5層防御**の対応が、④の文章だけでは追いにくい。 | 線表の主要マイルストーンに「対応する防御層」または「対応するパイプライン番号」を1列追加するか、短い注釈で対応関係を示す。 |
| **申請金額と必要経費の一致は不要**と明記されているのは良い。一方で、**必要経費の内訳**が「目安」であることが読者に伝わるようにする。 | 表の上または下に「上記はプロジェクト遂行に充てる目安であり、契約金額（作業時間ベース）とは無関係である」と一文あると、公募要領との整合が明確になる。 |

### ⑤ 提案者の腕前を証明できるもの

| 批判的指摘 | 改善案・どうすべきか |
|------------|----------------------|
| **本システムは既に公開運用中**で強みだが、「潜在空間は未実装」とあるため、未踏でやるのは**既存の上に足す部分**に読める。**自分でゼロから設計・実装した**ことが審査員に一目で分かるようにする必要がある。 | 「本システムの設計・実装はすべて自分で行った」ことを**明示的に1文**書く。未踏期間では「潜在空間の設計・実装と評価」を新規にやることを、①または⑤で一言添える。 |
| **受賞歴**は並べているが、**本プロジェクト（医薬品・NLP・安全性）と直結するもの**が少ない。審査員は「このテーマでこの人がやる必然性」を見る。 | 医薬品・相談業務と開発の接点（**登録販売者として得た知見を設計に活かしている**）を、⑤または①に**1〜2文で具体的に**書く。 |
| **資格（情報処理、登録販売者）**は書かれているが、**どう開発に活きるか**が短い。 | 「登録販売者としての知識をルール設計・用語選定に活かしている」「情報処理の知識をシステム設計に活かしている」など、1文でよいので結びつける。 |
| デモ動画「2〜3分を用意」は良い。**環境依存を避ける**理由も書かれていると、審査員への配慮として評価されやすい。 | 現状のまま維持でよい。可能なら「オフラインでも動作確認できる簡易版を用意する」など、一言あるとさらに良い。 |

### ⑥ プロジェクト遂行にあたっての特記事項

| 批判的指摘 | 改善案・どうすべきか |
|------------|----------------------|
| **アルバイト継続**と「プロジェクト開発を優先する時間を確保」の**両立の根拠**が薄い。1,295時間を約9ヶ月でこなすと**週あたり約37時間**になり、学業＋アルバイトとの整合が疑われる。 | **週の時間配分の概算**（学業○h、アルバイト○h、開発○h）を1行でもよいので示す。または「繁忙期はアルバイトを減らす」「夏休みは開発に集中する」など、**両立の具体策を1文**入れる。 |

## 3. その他（体裁・フォーマット）

| 項目 | 批判的指摘 | 改善案・どうすべきか |
|------|------------|----------------------|
| **ページ数** | 公募要領は「10ページ以内」。図表が多いため、**PDFが10ページを超えている可能性**がある。超えると審査対象外のリスク。 | 提出前に**PDFのページ数を確認**する。10ページを超える場合は、図の統合・縮小・文章の圧縮で10ページ以内に収める。 |

## 4. まとめ：審査員が「採択したい」と思うために

1. **①**：背景を圧縮し、「何をどこまで作るか」を冒頭で一言で言い切る。自分史は最小限に。
2. **②**：出し方の**順序**（普及→収益検討）を明確にし、ビジネスは「意図の例」に留める。
3. **③**：既存との差別化を**因果で**書く。数値（99%等）の**根拠**を必ず書く。
4. **④**：1,295時間の**按分計算を表または式で明示**。専門家監修のタイミングと回数を一致させる。
5. **⑤**：「自分で設計・実装した」ことと、**医薬品・登録販売者と開発の接点**を明示する。
6. **⑥**：学業・アルバイトと開発の**両立の具体策**（時間配分または優先方針）を1文入れる。
7. **⑦・⑧**：本プロジェクトとの**1文の接続**を入れると、一貫性が伝わる。
8. **全体**：PDFが**10ページ以内**か必ず確認し、生成AI利用の有無を明記する。

以上を反映すると、審査員に「計画が緻密で、出し方も考えており、このテーマでこの人がやる必然性がある」と伝わりやすくなる。
